## 1. 本轮目标

两件事，顺序不能反：

1. **审核**：判断当前开发进度与质量是否还有需要优化的地方 —— 不能只信门禁和阶段报告的结论；
2. **归档**：把本轮开发中归纳出的异常流程沉淀到文档，而不是留在对话里。

判定标准是**可执行的**：把「每个服务失败时到底吐什么」横向摆开对比，而不是逐个服务看它自不自洽。

## 2. 审核方法

| 手段 | 具体做法 |
|---|---|
| 跑全部门禁 | Java / Python / wp-bff / 契约 / 文档覆盖 / 前端 —— 先确认"成功路径"没问题 |
| **跨服务横向比对** | 对同一组反例（未映射路由 / 存在但方法不符 / 错误 Content-Type / 坏请求体），逐个服务打一遍，横向对比响应形状与状态码 |
| 错误形状反查 | `grep -rn "res.json({ *error\|{error:" services/node/wp-bff/server.js`；Java 看 `GlobalExceptionHandler` 落点；Python 看是否裸漏 FastAPI 默认体 |
| 覆盖范围盲区检查 | 检查各服务的 HTTP 层是否有对应测试（本轮发现 nlp-service **完全为零**） |

**为什么需要"横向"比对**：单服务测试永远只证明它自己自洽。
同一份 Phase 3 代码里，`{code,message,details}` / `{error}` / FastAPI 默认 `detail` 三种形状并存了很久，
而各自的门禁都是绿的 —— 直到把它们放在一起看才发现。

---

## 3. 审核结论：3 处真实缺口

| # | 缺口 | 危害 | 为什么门禁照不到 |
|---|---|---|---|
| 1 | **错误信封三种形状**：Java `{code,message,details}` / wp-bff `{error}` / nlp-service 裸漏 FastAPI 默认体（`detail`） | 客户端要写三套解析逻辑，前端 `status.ts` 无法统一登记状态徽标 | 契约只校验端点存在与否，**不约束错误响应体形状** |
| 2 | **wp-bff 对"方法不支持"返回 404**，而 Java 三服务返回 405 | 同名语义相反：把"用错方法"伪装成"端点不存在"，排查方向被直接带偏 | 单服务各自自洽；**没有测试断言"同 vs 不同服务语义一致"** |
| 3 | **nlp-service HTTP 层零测试**（52 项全在业务层） | 异常映射改了没人拦 | 覆盖率统计按文件/包维度，**看不出某一层没有测试** |

## 4. 修复明细

### 4.1 wp-bff：统一出口 + 路由层 405 分流

| 改动 | 说明 |
|---|---|
| 新增 `fail(req, res, status, code, message, details={})` | 唯一的错误出口；全站错误体形状归一 |
| `authorizeControl()` 改为返回 `{ok, status, code, message, details}` | 旧 `error` 字段不再出现；401 → `AGENT_UNAUTHORIZED`、403 → `AGENT_FORBIDDEN` |
| 新增 `ROUTE_GUARD` | **由 `IMPLEMENTED_ENDPOINTS` 派生** —— 刻意不引入第三份端点真相。路径存在但方法不符 → 405 + `Allow` 头；否则 404 |
| 清理 5 处残留 `{error}` 错误体 | whitelist 拒绝 / 请求体校验等场景统一改走 `fail()` |

### 4.2 nlp-service：注入三个异常处理器

| 处理器 | 行为 |
|---|---|
| `StarletteHTTPException` | 404 / 405 透传（405 带 `Allow` 头）；**422 归并为 400** |
| `RequestValidationError` | 400 + **字段级 details**（如 `texts.0`） |
| 兜底 `Exception` | 500，**只记日志，不泄露内部信息** |

配套 `_agent_code()` 做 HTTP 状态码 → `AGENT_*` 错误码映射。

### 4.3 契约

`contracts/work-platform-bff-openapi.yaml` 头部补统一错误信封约定；新增 `ErrorEnvelope` schema
（**11 个错误码枚举**）与 `components.responses.ErrorEnvelope`；implemented 端点补 404/405 声明，
400/401/403 补 schema 引用。

### 4.4 测试补齐

| 服务 | 变化 | 新增用例 |
|---|---|---|
| wp-bff | **29 → 34**（+5） | 404 信封 / 405 + `Allow` / 参数化路径 405 / `ROUTE_GUARD` 派生一致性 / **鉴权失败不触达下游** |
| nlp-service | **52 → 62**（+10） | 新增 `tests/test_http_errors.py`（该服务首个 HTTP 层测试） |

## 10. 关键教训

**门禁全绿 ≠ 失败路径正确。**

130 个用例、0 FAIL 契约、106/106 文档覆盖，全部只对**成功路径**设防；
本轮三处缺口无一例外藏在**错误分支**里。

推论：**横切关注点（错误形状、鉴权口径、状态码语义）必须做"跨服务一致性"检查**，
而不能靠单服务自己的测试 —— 单服务测试永远只证明它自己自洽。
