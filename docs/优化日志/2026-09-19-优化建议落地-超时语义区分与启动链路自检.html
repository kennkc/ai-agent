2. 缺陷一：上游把「慢」和「没有」合并成同一个 null¶

2.1 问题的本质¶

上一轮在服务侧把沙箱探测改成非阻塞（5.7s → 0.5s），但表达层的问题没动：

// 修复前
function httpRequestJson(url, { ... } = {}) {
  return new Promise(resolve => {
    ...
    request.on('timeout', () => { request.destroy(); resolve(null) })
    request.on('error',   () => resolve(null))
    response.on('end',    () => { try { resolve(JSON.parse(raw)) } catch { resolve(null) } })
  })
}

四种完全不同的失败——对端太慢 / 对端没起 / 端点不存在 / 返回不是 JSON——全部 resolve(null)。 调用方拿到 null 只能写一句"不可用"。于是：

  • 沙箱探测冷启动慢 5.7s → 被叙述成 "沙箱不可用"
  • tool-executor 是旧版本、没有 /api/tool/sandbox → 同样被叙述成 "沙箱不可用"
  • 服务真的没起 → 还是 "沙箱不可用"

三者运维动作完全不同（重试 / 重启服务 / 升级服务），却给出同一句话。

2.2 修复¶

新增 httpRequestJsonMeta()，返回结构化的失败原因：

{ ok: true,  data: {...}, status: 200 }
{ ok: false, data: null,  reason: 'timeout'|'unreachable'|'endpoint_missing'|'http_error'|'bad_json', status?: number }

404 单独识别为 endpoint_missing（版本不匹配的强信号，与"服务不可达"是两回事）。 原 httpRequestJson 保留为丢弃原因后的薄封装 —— 既有 73 条用例零改动全绿，向后兼容。

2.3 工具域聚合升级¶

partial_reasons: ['sandbox_timeout']      ← 慢
partial_reasons: ['sandbox_missing']      ← 端点不存在（版本旧）
partial_reasons: ['sandbox_unavailable']  ← 真连不上

同时新增三个字段：

字段 用途
reason_code 整体不可用时的机器码，供前端分支
partial_note 人类可读解释（"对端未在预算内返回 —— 这是慢，不是没有"）
probe_budget_ms {default, sandbox} 各子请求预算，排查用

另外把沙箱分片单独放宽超时预算 —— 它是唯一会触发容器探测的子请求，用与普通读端点 相同的预算本身就是设计错配。

预算口径更正（同日复核）：本文件初稿写"上游 2500ms 预算"，实际工具域走的是 httpRequestJson 默认 5000ms（WP_BFF_TOOL_TIMEOUT_MS 现在显式化为 5000，沙箱 8000）。 httpGetJson(url, timeoutMs = 2500) 是另一个仅 GET 的辅助函数，与工具域无关 —— 两者都在 server.js 里且都是超时默认值，极易混淆。更正后余量只有 0.7s，比初稿描述的更脆弱。 详见《2026-09-19-工作平台真实链路打通与沙箱探测非阻塞化》§3.2 的口径更正。

2.4 前端侧¶

ExecutionView.vue 新增 PARTIAL_REASON_LABELS 映射表，分片缺失告警不再打印 raw code：

sandbox_timeout → 「沙箱状态读取超时（慢，非缺失）」
sandbox_missing → 「沙箱端点不存在（服务版本可能较旧）」

3. 缺陷二：vite 代理目标与 BFF 端口无交叉校验¶

3.1 为什么危险¶

WP_BFF_URL（前端代理目标）与 WP_BFF_PORT（wp-bff 监听端口）是两个互不校验的环境变量。 端口一错，页面不会报错：

请求 → 500 → api/provider.ts 的 safe() 兜住 → 逐 scope reportDegrade() → 回落 Mock

用户看到的是「满屏演示数据 + 顶栏一堆降级」，从页面上无法判断这是环境问题。 上一轮实测就踩到了：BFF 落在 8090，代理想指别处。

3.2 修复¶

vite.config.ts 新增 bffReachabilityGate() 插件：

  • 启动期探活：对 WP_BFF_URL 与 WP_GATEWAY_URL 各打一次 /api/wp/healthz（gateway 打根路径）
  • 不可达 → 终端醒目告警，直接给出 WP_BFF_URL 当前值与 WP_BFF_PORT 的排查提示
  • 每条目标只响一次，不刷屏
  • 非阻塞（异步探活，不拖慢 dev server 启动）

实测验证：WP_BFF_URL=http://127.0.0.1:9999 起 vite → 终端输出告警； 经该实例打代理请求失败但进程不崩（无未捕获异常），3001/3099 监听正常。

4.2 healthcheck 的 set -e 自杀缺陷（本轮新发现）¶

set -e
check_http() { code=$(curl -s --noproxy "*" -o NUL -w "%{http_code}" --max-time 5 "$url" 2>/dev/null); ... }

问题：命令替换里，code=$(...) 这个赋值的退出码 = curl 的退出码。 curl 连不上时以非 0 退出（如 7 = Failed to connect），配合 set -e → 脚本在第一个不可达服务处直接终止。

也就是说：这个脚本恰好在它最该工作的场景下失效 —— 服务挂掉时它报不出来， 只会安静地少输出一半。实测 exit=7，[java services] 之后一行都没有。

修法： - 命令替换加 || true，把非 0 退出码吃掉 - -o NUL 改为 -o /dev/null（NUL 依赖 Windows 设备名，Git Bash 下不可靠）

6. 留下的思考¶

同一类错误在本轮出现了三次，形状完全一致：

  1. DockerSandboxBackend.available() 在请求线程同步跑 docker CLI → 慢被表达成没有
  2. httpRequestJson 把所有失败塌缩成 null → 原因被表达成没有
  3. healthcheck.sh 的 set -e → 脚本在"发现故障"这个动作上失败，于是故障被表达成没有

三处的共同点：下游只拿到一个空值，就丢失了全部可行动信息。 这不是三个孤立的 bug，是同一个认知缺陷的三次显形 —— 值得作为后续评审的一条检查项：

任何 null / false / 空数组的返回点，问一句「调用方还能区分出哪几种情况？如果只剩一种， 那运维动作是不是就无从下手了？」

另一条更窄但更实际的：跨服务超时预算的乘积关系没有守门。 BFF 给子请求 5000ms，服务侧操作 5700ms —— 两个数字各自合理，相遇即错，且只差 0.7s。 本机无法用单测覆盖（要真起服务 + 真慢），只能靠运行态实测发现。 已记入 docs/技术债台账.md（跨服务超时预算）。
