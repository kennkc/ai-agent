## 1. 起点：REC-01 轮留下的三条 gap

| # | 边 | 问题 | 余量比 |
|---|---|---|---|
| GAP-01 | session → nlp `/brain/ask` | 上游 30s 对下游最坏 22s | 0.91x |
| GAP-05 | nlp → body 检索 | 上游 8s < 下游读超时 10s | 0.80x |
| GAP-06 | wp-bff → session `/ask` | GENERATE 45s 对 session 总预算 35s | 1.29x |

三条的 fix_hint 各给了两个方向。本轮统一选**内层收敛、外层覆盖**（REC-01 的哲学），
而不是把上游超时层层抬高 —— 那会把「快速失败并降级」变成「长时间等待后仍降级」。

## 2. 三条怎么闭合的

### 2.1 GAP-01：收紧 nlp 上限，而不是抬高 session 上游

选了 fix_hint ②：`BRAIN_TOTAL_BUDGET_MS` 25s → **20s**。

**为什么原 25s 等于没有**：级联推导最坏 22s < 25s，预算从不构成约束 ——
"有预算"和"预算有用"是两回事。收紧到 20s 后它成为**真正的硬上限**，
级联（L2 8s×2 + L1 3s×2 = 22s）在预算内被截断，session `BRAIN_TIMEOUT` 30s 对它恰好 1.5x。

**为什么不选 ①（上游抬到 33s）**：session 总预算 = 意图 5s + 生成 33s = 38s，
GAP-06 会从 45s/35s=1.29x 恶化到需要 ≥57s 才能盖住 —— **余量比是两侧的函数，
闭合一处前先看它对相邻边的推挤**。

> **取舍如实登记**：20s 预算意味着检索若吃满 15s（GAP-05 闭合后的新值），
> 生成只剩 5s —— L1 单次 3s 够用，重试会被截断。这是刻意的：下游病态变慢时
> **更快失败**，正是 deadline 的本意。

### 2.2 GAP-05：修掉一个登记表失真，再闭合倒挂

复查 body `/retrieve` 真实管线时发现，表里 TB-16 的下游最坏 "10s" 本身就是**失真**：

```text
登记依据：「body-service OutboundHttp DEFAULT_READ_TIMEOUT = 10s」
真实管线：查询向量化（nlp embed 预算 12s）→ Qdrant（2s）→ 重排（读超时 10s）
真实端到端最坏 ≈ 24s，不是 10s —— 表把「单个出站读超时」误当成了「端到端最坏」
```

**教训：登记表里"下游最坏耗时"必须是端到端的最坏，不能拿某一跳的读超时冒充 ——
否则门禁的余量比是从假数字算出来的。**

修法与 REC-01 同路线：

1. body-service 新增 **`common/BudgetGuard.java`**（约 100 行）：
   warm 管线（嵌入 + Qdrant + 重排）在 `RETRIEVAL_TOTAL_BUDGET_MS = 10s` 端到端预算内执行，
   超时抛 `AGENT_TIMEOUT`（→ 504），**绝不返回空结果冒充"无结果"**（检索是 Must 项）；
   语义与 Python 侧 `run_with_budget` 对齐（`<=0 = 显式不限`；诚实边界：工作线程不可强杀）。
2. nlp 上游 `RETRIEVAL_BUDGET_MS` 8s → **15s**（15s / 10s = 1.5x）。
3. **口径合一**：废除 `RETRIEVAL_TIMEOUT_SECONDS`（与 `RETRIEVAL_BUDGET_MS` 同值不同名，
   是潜在漂移源）；`retrieval.py` 的 `DEFAULT_TIMEOUT` 改由 `budget.py` 派生（毫秒→秒换算）。

### 2.3 GAP-06：单列档位，不动 GENERATE

wp-bff 新增 **`ASK_TIMEOUT_MS = 53000`**（35s × 1.5 = 52.5s），
只服务 `POST /api/session/{id}/ask` 这一条边；**GENERATE 档保持 45s 不动** ——
它被 `/brain/ask`、`memory/ingest|compress` 等多条边共享，抬高会把那些
"快速失败并降级"的边一起拖慢。用例同步加了防退化断言：**ASK 必须严格大于 GENERATE**
（两档被合并回一个值 = GAP-06 复发）。

## 3. 测试揭出的写用例陷阱

首轮 `warmPipelineOverBudgetSurfacesAsTimeoutNotEmptyResult` 假绿（预算 200ms、7ms 正常返回）。

**根因**：检索链路调的是 `embeddingClient.embedOne(...)`，而用例 stub 的是它内部的
`embed(...)` —— mock 拦截层根本不会走到真实方法体，所以 stub 被静默跳过，
管线拿到 Mockito 默认空值照常跑完。

**修法**：stub 打在**实际被调用的那一层**（`embedOne`）。已把这条写进用例注释。

> 与本轮另一条认知同源：**stub / 锚点 / 断言，都必须精确锚定在被验证的边界上**，
> 锚松了不是"没验证"，是"假装验证了"。

## 7. 认知沉淀

1. **"有预算" ≠ "预算有用"** —— 上限大于最坏耗时的预算从不构成约束，等于装饰。
   收紧到能咬住最坏路径，才算数。
2. **余量比是两侧的函数** —— 闭合一处缺口前，先算它对相邻边的推挤
   （GAP-01 若选"抬上游"会把 GAP-06 恶化一档）。
3. **登记表的数字必须是端到端的最坏** —— 拿单个出站读超时冒充端到端最坏，
   门禁的余量比就是从假数字算出来的。
4. **stub 必须打在被调用的那一层** —— mock 拦截层之下不会被走到，stub 错层即假绿。
