MC-01 可靠性加固与端到端消费闭环（2026-09-20）¶

范围：MC-01 协作总线独立切片（Phase 6 前置） · 性质：可靠性缺陷修复 + CI 门禁补强
结论：R-MC01-01~04 从“基础能力完成”推进到“真实 durable consumer 可恢复、可重投、可死信、可 CI 验证”

1. 本轮修复的问题¶

问题 修复前风险 本轮处置
真实 JetStream 消费循环缺失 IdempotentConsumer 只是 helper，消息不会被 ack/nak 新增每域 durable pull consumer + 虚拟线程拉取循环
失败重投语义冲突 先标 seen 且失败不回滚，重投被误判重复，无法进 DLQ 改为 pending / processed / failed / dlq 状态机
关键集成测试在 CI 跳过 离线恢复、幂等、DLQ 只在本地手工验证 新增 collab-integration job（PostgreSQL + NATS）
心跳限流只打标记 高频心跳仍每次写 PG，防风暴未真正生效 5 秒窗口合并，pending 查询可见，窗口 flush 落库
域创建半成品 PG 已写 active、stream/consumer 创建失败时留下孤儿域 引入 creating → active / failed，失败补偿 + 启动对账
旧 push consumer 无法恢复 重启时配置漂移导致无法绑定 安全迁移为 durable pull；有未处理消息时拒绝自动迁移并显式暴露

2. 关键实现¶

  • 发布协议：NATS headers 携带 X-Tenant-Id / X-Request-Id / X-Member-Id / X-Message-Type，JetStream message-id 使用 request_id。
  • 消费状态机：首次 CLAIMED；失败 RETRY；成功 processed；达到 retry-max + 1 后自动发布 deadletter 并 ack 原消息。
  • 消费者恢复：durable pull consumer 从未 ack 位置继续；每域后台拉取，不用固定 deliver subject，重启可重新绑定。
  • 心跳窗口：窗口内只覆盖 pending 中最后值；查询合并 pending；默认每 5 秒最多 flush 一次。
  • 健康可见：GET /api/collab/health 增加 consumer 与 heartbeat 运行态。
