优化日志：REC-01 —— LLM 级联总预算与跨服务预算同步（2026-09-19）¶

上游文档：docs/优化日志/2026-09-19-跨服务超时预算登记表与门禁落地.md（同日上一轮） 登记表：contracts/timeout-budget.yaml · 门禁：scripts/timeout-budget-check.py

1. 起点：两条缺口其实是同一个病¶

上一轮结束时留了 5 条 gap。翻回去看，「最根本」的两类其实是同一个根因的两种表现：

缺口 表述 本质
REC-01 LLM 级联最坏耗时 = 「各级超时 × 重试次数」的乘积 下游没有自己的时间上限，所以它的最坏耗时不可控
GAP-03 / GAP-04 Python 侧 /embed、/ocr 无独立超时 下游没有自己的时间上限，所以它的最坏耗时不可证明

一句话："下游最坏耗时"这个数字，在缺少下游自身上限时，要么是乘积（不可控），要么是猜（不可证明）。 于是「上游预算 ≥ 下游最坏 × 1.5」这条不变量，在数据源头上就站不住。

结论：不能靠不断调大上游超时去"覆盖"一个会自己膨胀的下游。 正确做法是给下游一个共享的总预算，让"最坏耗时"变成一个常量。这就是 deadline propagation。

2. 做了什么¶

2.1 Python 侧（nlp-service）：把"被赋予的超时"变成"自己持有的预算"¶

新增 app/budget.py：

名字 值 作用
run_with_budget(fn, budget_ms, operation=…) — 在预算内执行；超时抛 BudgetExceeded，不返回空值冒充"没有数据"
BudgetExceeded — 携带 operation / budget_ms / elapsed_ms，供上层如实转 504
Deadline — 级联/重试共享的预算对象，提供 clamp(单步超时) / remaining_ms() / note_exhausted()
deadline_at(ms) / remaining_from(ts) — 把截止点放进 LangGraph 的 state 跨节点传递（放实例上会被并发调用互相缩短预算）
预算常量 默认 适用
BRAIN_TOTAL_BUDGET_MS 25000 /brain/ask 的检索 + 生成共享预算
EMBED_BUDGET_MS 12000 /api/nlp/embed
OCR_BUDGET_MS 12000 /api/nlp/ocr
RETRIEVAL_BUDGET_MS 8000 RAG 检索段（并收窄 RETRIEVAL_TIMEOUT_SECONDS）

超时统一按 504 AGENT_TIMEOUT 返回（app/main.py 的错误码映射），不塌缩成 500。

2.2 级联内部：每一级都在"剩余预算"内调度¶

LlmGateway.generate(request, deadline_ms=…)：级联每一级、每一次重试的可用超时取 min(该级超时, 剩余预算)；预算耗尽的瞬间不再发起新的调用，并把这次失败计入 deadline_exceeded 统计（与"引擎不可用"分开计数）—— 前者是"时间用完了"，后者是故障。

RagPipeline.run(..., deadline_ms=…)：检索与生成共享同一个 deadline。 生成拿到的是"扣掉检索耗时后的余额"，于是「整条链路 ≤ 预算」由构造保证， 而不是靠各级超时恰好加起来够用。

2.3 Java 侧（session-manager）：具名档位 + 请求级预算¶

新增 orchestration/RequestBudget：入口处创建（一次 ask = ASK_TOTAL_BUDGET_MS 35s = 意图 5s + 生成 30s）， 每一跳读超时取 min(该跳档位, 剩余预算)；剩余为 0 时不再发起调用，如实降级并标注 budget_exhausted。

档位 值 用途
INTENT_TIMEOUT 5s nlp 意图识别（规则级联，毫秒级）
RETRIEVE_TIMEOUT 15s body 检索
BRAIN_TIMEOUT 30s nlp /brain/ask 生成
DEFAULT_READ_TIMEOUT 10s 兜底（未声明用途的读）

落点：NlpClient / BodyClient / BrainClient 分别改用对应档位（原先一律吃 DEFAULT_READ_TIMEOUT）， SessionController 的 ask 链路接上 RequestBudget。

3. 本轮最重要的东西：一个被测试抓出来的真缺陷¶

3.1 现象¶

跑全量 pytest 时红了一条：

tests/test_budget.py::test_budget_exhausted_before_retrieval_skips_downstream_and_reports_why
E   AssertionError: assert 'template' == 'none'

预算是 1ms，却仍然生成出了一个答案（generator='template'）。这不是测试写错，是真缺陷。

3.2 根因：一个约定，把"耗尽"翻译成了"不限"¶

Deadline / run_with_budget 有一条既定且有测试守着的约定：

None / 0 表示「不限」 —— 这是显式选择，不是遗漏。 （test_budget_none_means_unlimited_not_zero 就是守它的）

这条约定在配置层是合理的：不能把"没配置"读成"0 秒内必须完成"。

问题出在传播层：管线从 remaining_from() 拿到的是算出来的剩余， 当它等于 0 时，含义是"时间到了"，可它被原样传给网关后，被同一条约定读成了 "不限" —— 于是：

检索吃光预算 → 剩余 = 0 → gateway.generate(deadline_ms=0)
                              ↓ 被约定读成"不限"
                          级联按各级超时全速跑（最长 22s+）

后果：REC-01 宣称的「整条链路 ≤ 预算」，在任何有检索的问答里其实并不成立。 更糟的是它不报错：答案还更"完整"了，只是慢得超出上游预算，最终由上游把"慢"判成"大脑层不可用" —— 正是本轮要消灭的那个形状。

3.3 修法：约定不动，改在"不得把耗尽表达成 0"这一层¶

这是本轮唯一需要判断力的地方。两条路：

选项 评价
把 0 = 不限 改成 0 = 耗尽 ❌ 会推翻一条有测试守的既定约定，且让"未配置"变成"立刻失败"
在管线层拦住：剩余为 0 时不发起生成 ✅ 约定语义不变，只在表达处禁止歧义

选择后者 —— 在 _node_generate 计算完 remaining_ms 后直接拦住：

remaining_ms = remaining_from(state.get("deadline_at"))
if remaining_ms is not None and remaining_ms <= 0:
    reason = f"budget_exhausted_before_generation (budget={state.get('deadline_ms')}ms)"
    ...  # 不发起生成，如实标注原因（不是「引擎不可用」）

认知：0 = 不限 这种约定，必须配一条"上游不得把耗尽表达成 0"。 否则约定本身就变成漏洞的载体 —— 它把"没有时间了"和"没有上限"合并成了同一个字节。

3.4 反向验证（做门禁的那套规矩，同样适用于"修 bug"）¶

把守卫临时短路成 if False and … 后复跑：

FAILED tests/test_budget.py::test_generation_is_stopped_when_retrieval_ate_the_whole_budget
E   Left contains one more item: 0      ← 网关确实被以 deadline_ms=0（=不限）调用了

断言输出直指"以 0 调用了网关"，证明用例抓的是真行为而非巧合；还原后转绿。

3.5 顺手修掉一个"赌时序"的用例¶

原用例用 deadline_ms=1 构造"预算已耗尽"，并在两次调用之间 sleep(0.02) —— 这等于赌"这 1ms 内确实发生了工作量"，机器快时会变成"预算还没用完"，测试随时序时红时绿。 改为直接把截止点设到过去（monotonic() - 1）：「已耗尽」是被构造出来的事实，不是概率。

同时把观测点从"整条管线"收到 _node_generate：整条跑的话，零 chunk 会先走 insufficient 分支、 根本到不了生成步 —— 那样的断言会因为走错分支而变绿，等于没守。

4.2 GAP-06 不是回归，是"变可信"的代价¶

之前 现在
session 一次 ask 的下游最坏 只说得出"单体读超时 10s" 35s 总预算（硬上限）
wp-bff GENERATE 档 45s 的余量 看起来很充足 1.29x，薄于约定 1.5x

同一件事，两种读法：下游最坏从"说不清"变成"说得清"，代价是上游余量比被摊薄。 这不该被藏起来 —— 所以登记为新 gap，而不是"反正没红"。

本轮最该记住的一条：给下游加预算上限会同时改变上游余量比。 闭合一个缺口可能制造另一个 —— 两侧必须同轮复核。

4.3 门禁自身的缺陷也暴露了一个¶

同步过程中发现：原锚点正则

READ_TIMEOUT = Duration\.ofSeconds\((\d+)\)

会子串命中 DEFAULT_READ_TIMEOUT（DEFAULT_ + 匹配）—— 于是 TB-11 / TB-12 长期读到的是兜底档的 10s，而不是它们真正的具名档， 门禁不报漂移、全绿。这与上一轮"锚点看不见调用点魔法数字"是同一类盲区的不同表现： 锚点锚得太松，等于没锚。

修法：锚点改为具名档位（BRAIN_TIMEOUT / RETRIEVE_TIMEOUT）， 并给 TB-09 / TB-13 / TB-15 补上下游锚点（ASK_TOTAL_BUDGET_MS、EMBED_BUDGET_MS、OCR_BUDGET_MS）， 让"下游最坏耗时"这个数字也有代码出处，而不只是一个声明。

7. 认知沉淀¶

  1. "下游没有上限"是一个根因，不是一个参数没填。 它同时制造了"不可控"（乘积膨胀）和"不可证明"（算不出余量）两种缺口。 修法也只有一个：给下游一个共享的总预算，让最坏耗时变成常量。

  2. 约定会变成漏洞的载体。 0 = 不限 本身没错，错在"上游把耗尽表达成 0"。 凡是把两种语义压进同一个值的约定，都要额外规定谁不得产生歧义值。

  3. 闭合一个缺口可能制造另一个。 余量比是两侧的函数： 把下游最坏从"说不清"改成"说得清"，上游那个原本够用的数字可能立刻不够了。

  4. 锚点锚得太松，等于没锚。 门禁两次栽在同一处： 先是"只看常量定义、看不见调用点魔法数字"，后是"子串命中兜底常量"。 ——门禁的价值取决于它锚的边界有多精确，不取决于它跑了多少条规则。

  5. "极小值"不是"确定耗尽"。 用 deadline_ms=1 构造耗尽状态是在赌时序； 要么把截止点构造到过去，要么把观测点收到能确定观测的那一层。 测试的确定性要来自构造，而不是来自概率。
