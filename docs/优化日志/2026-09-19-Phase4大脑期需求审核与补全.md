## 3. 审核结论

### 3.1 伪代码排查：扫描 0 处标记，但**通读发现 2 处实质伪实现**

`grep` 层面：**0 处** `TODO/FIXME/占位/dummy/fake/stub` 出现在业务源码中
（`proto-contracts` 的 `Stub` 命中项是 protoc 生成的 gRPC 类名，属正常产物；
`web/work-platform/dist/**` 命中项是**构建产物且已入库**，见 §3.5）。

但**通读核心算法后**，发现 2 处"注释/自述与行为不符"的实质伪实现 —— 这类问题 `grep` 抓不到，
只有把"它声称做什么"与"它实际做什么"摆在一起才看得见：

#### 🔴 A1 · R4-04 语义缓存的「Redis 后端」是空壳（谎报后端）

| 项 | 内容 |
|---|---|
| **证据** | `services/python/nlp-service/app/brain/semantic_cache.py:93-100`（保存 `_redis`）、`:152/158/160/165/169/173/176/179`（**读写路径全部只操作 `self._local` 进程内字典**） |
| **声称** | 类注释 `:3`「存储：Redis（复用 Phase 3 的 lifeform-redis）；Redis 不可用时降级为进程内缓存」；`health()` 在 Redis 连通时回 `backend=redis, degraded=false` |
| **实际** | `self._redis` 在 `__init__` 之外**零引用** —— `store()` 只写 `_local`，`lookup()` 只扫 `_local`。Redis 通与不通，行为完全一致，唯一差别是 `backend` 字段的**字符串** |
| **后果** | ① 进程重启即失忆、多实例不共享（设计口径"复用 Redis"落空）；② `health()` 报 `redis` 而数据实为内存，属**谎报**；③ 阶段报告据此写下"真实 Redis 后端，非内存兜底"（见 E1） |
| **为何单测抓不到** | `tests/test_brain.py` 全部用例构造 `SemanticCache(redis_client=None, ...)` → **Redis 路径零覆盖**，测试只证明了"内存兜底自洽" |
| **定性** | **伪实现（红线）** —— 不是"能力缺失但诚实上报"，而是"声称用了 Redis 实际没用" |

#### 🔴 A2 · D5 决策链回放端点永远返回「成功 + 空链」（静默假装成功）

| 项 | 内容 |
|---|---|
| **证据** | `services/node/wp-bff/server.js:702-724` |
| **声称** | 函数注释 `:700`「未命中时返回 404（**未找到就是 404，不用 200 + 空数据冒充成功**）」；契约 `contracts/work-platform-bff-openapi.yaml:841`「决策链回放（D5，**读 IN3 AuditLog**）」，声明 404/405 |
| **实际** | 只要 `nlp-service` 活着，无论 `decision_id` 是什么，一律 `200 + {available:true, chain:[], note:…}` —— **404 分支根本不存在**；且全库 `grep -rln "AuditLog\|audit_log"` 仅有 `pipeline.py` 一处注释命中，**不存在任何 AuditLog 实现** |
| **后果** | ① 任意合法格式的 decision_id 都能"回放成功"，只是链为空 → 前端无法区分"没这条决策"与"回放失败"；② 违反本仓库已定型的 planned 三态口径（404=未实现/不存在）；③ 契约声明 404 而实现没有 → 客户端按契约写的错误处理永远不会触发 |
| **为何单测抓不到** | `services/node/wp-bff/test/server.test.js:647` 用例名为「决策链回放端点**可达**」，只断言 `data.decision_id === 'b6c3bd94'`，**没有断言 available / 404 语义** → 测试反而固化了空壳行为 |
| **定性** | **伪实现（红线）** —— 注释写了 404，代码给了 200；属"静默假装成功" |

### 3.3 链路可达性：**session-manager 在端到端链路上是孤岛**

| 链路 | 现状 | 判定 |
|---|---|---|
| work-platform → BFF → nlp 大脑层 | `ChatView.vue:178` → `provider.ts:259 POST /brain/ask` → `server.js:737` → nlp | ✅ 通 |
| Console → BFF → nlp 大脑层 | `provider.js:239` → `/api/wp/brain/ask` | ✅ 通 |
| **前端 → session-manager（FSM / Redis 会话）** | **不存在** | 🔴 断 |

证据：

- `services/node/wp-bff/server.js` 全文**没有代理任何 `/api/session` 端点**，`sessionUrl` 只在 `:688-691` 被拼成一个字符串塞进 `sessions.source` 返回给前端（注释自述"BFF 不做二次汇总"）；
- `web/work-platform/src/views/ChatView.vue:120` `taskId = route.query.task_id || 'T-1042'`，`:178` 把 `taskId` 当 `session_id` 传给大脑层 —— **任务号不是会话号**；
- 同文件 `:173-174` 多轮上下文取 `messages.value.slice(-7, -1)`，即**前端内存数组**，刷新即丢失；
- `web/console/index.html:151` 用一个**静态常量**当会话号（注释却写"与 session-manager 的 session_id 对应"）。

后果（直接冲击 DoD）：

- DoD「多轮对话上下文保持（连续 5 轮不串）」—— 现阶段靠浏览器内存撑着，**刷新即断**；
- DoD「服务重启会话可恢复」（R4-02 验收标准）—— 会话真相在 Redis，但**没有任何产品链路写入或读取它**，Redis 里只有端到端脚本手动造的会话；
- R4-09「会话管理」与 R-C04「大脑视图展示**活跃会话**」—— 均无真实数据源。

> 与 Phase 3 复审同一类问题：**实现了、单测过了、端到端脚本（直连 8081）也过了，但产品链路不走它**。
> 差别是 Phase 3 那次是"知识入库链路断"，这次是"会话链路断"。

## 5. 需要你拍板的三件事

**Q2 · R4-07 缺口阈值 0.85 → 0.35 是否确认改设计文档？**

- 但需求文档 §6 原文写的 0.85 属**口径变更**，需你点头后我才能改设计文档（或选择"保留 0.85 作为目标值、等 DEBT-010/011 闭合再回落"）。

**Q3 · IN-02 记忆图谱 / 会话链路 是否在 Phase 4 内补？**
- IN-02 是 Should、2 人天；会话链路补 BFF 代理约 1 人天；
