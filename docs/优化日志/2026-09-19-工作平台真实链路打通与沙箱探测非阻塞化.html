2.2 根因¶

vite.config.ts 的代理默认端口（8090）与 wp-bff 的 WP_BFF_PORT 是两个独立变量、无任何交叉校验。 端口一错，界面就静默退化成「满屏 Mock + 一堆降级」，从页面上完全看不出是环境问题。

2.3 处置¶

  • 以最新代码在 8090 起 wp-bff（前端零改动，因 vite 默认代理口即 8090）。
  • 令牌文件路径两侧一致（services/node/wp-bff/logs/wp-bff-control-token），新实例启动后重新落盘， vite 每请求动态读取 → 自动对齐，写路径不会因令牌过期而 403。
  • 清理 8095 僵尸实例（Phase 3 验收遗留，见 Phase3-开发执行日志.md 第 222 行"8090 被占用 → 改在 8095 验收"）： 它没有 Phase 4/5 端点（/tools、/brain/ask、/session/stats 全 404）， 且新实例已覆盖令牌文件 → 留着只会让写路径必然 403。

3. 缺陷二：沙箱探测阻塞请求线程（代码层，本轮主要修复）¶

3.1 现象¶

工具域已能连上，但 GET /api/wp/tools 返回：

{ "sandbox": null, "partial": true, "partial_reasons": ["sandbox_unavailable"] }

而直连服务端点 GET /api/tool/sandbox 其实是 200，只是耗时 5.7 秒。

3.2 定位¶

环节 事实 出处
上游预算 httpRequestJson(url, {..., timeoutMs = 5000}) 的默认值 —— 工具域聚合调用时未传 timeoutMs，故实际预算是 5000ms services/node/wp-bff/server.js:55（HEAD 版）
服务侧探测 docker info（5000ms 超时）+ docker image inspect（5000ms 超时），在请求线程内同步执行 DockerSandboxBackend.available() 原实现
实测冷探测 5.7s（Windows Docker Desktop 上单次 docker CLI 约 2.5s，两次叠加） 两次独立计时
结果 5.7s > 5.0s → BFF 超时（余量仅 0.7s）→ 落 null → 视图显示"沙箱不可用" —

口径更正（2026-09-19 复核）：本节初稿把上游预算写成 httpGetJson(url, timeoutMs = 2500) （server.js:37）—— 那是另一个仅 GET 的辅助函数（fetchJson，供其他数据域用）， 与工具域聚合无关。工具域走的是 jsonRequest → httpRequestJson，默认 5000ms。 两处都在 server.js 里且都是超时默认值，混淆成本极低，故保留更正痕迹。 更正后的结论更严峻：真实余量只有 0.7s（不是 3.2s），意味着任何一次负载抖动都会复发。

curl /api/tool/sandbox      → 200，5.7s（服务侧"能答，只是慢"）
BFF 内部请求（5.0s 预算）   → 超时 → 落 null
GET /api/wp/tools           → sandbox:null + partial:["sandbox_unavailable"]
执行视图                    → "沙箱不可用"（与实际完全相反）

这是一类值得警惕的缺陷模式：一个「慢」被上游表达成了「没有」。 更隐蔽的是 —— Phase 5 早期确实对应「镜像未构建」，所以这个错误结论看起来一直是对的； 直到镜像构建完成、available() 真为 true 之后仍继续误报，才暴露出来。

3.3 修复¶

把「可用性探测」从请求路径上摘下来：

行为 时机 说明
同步探测 仅启动一次（构造器内） 使启动日志与首个请求都能拿到真实结论
available() 任意时刻 恒 O(1) 返回缓存值；缓存过期时投递后台守护线程刷新后立即返回
门闩 refreshing（AtomicBoolean） 并发查询 同一时刻至多一个刷新在飞，避免探针风暴
15s TTL（PROBE_TTL_MS） 缓存有效期 保持原语义不变

同时抽出 BooleanSupplier prober 与 probeTtlMs 两个测试接缝，使"性能契约"可被断言 —— 这类契约不会让任何功能用例失败，只会让上游悄悄降级，因此必须显式守住。

5. 遗留与建议¶

# 事项 说明
1 BFF 超时语义（建议项，未改） BFF 把「超时」与「不可用」合并成同一个 null。本次在服务侧根治，但该模式仍在：任何慢子请求都会被表达为"缺失"。若要根治，应在 httpGetJson 里区分 timeout 与 error，并把 partial_reasons 分成 *_timeout / *_unavailable。改动会触及 73 条 wp-bff 用例，未擅自进行
2 端口无交叉校验（建议项，未改） vite 代理 8090 与 WP_BFF_PORT 各自独立。可加启动期自检（目标不可达时终端醒目告警）或把端口固化为脚本常量
3 后台进程不持久 8090 BFF 与 8084 tool-executor 均为后台进程，重启后需手动再起：
cd services/node/wp-bff && WP_BFF_PORT=8090 node server.js
cd services/java/tool-executor && java -jar target/tool-executor-0.1.0-SNAPSHOT.jar --spring.cloud.nacos.discovery.enabled=false --spring.cloud.nacos.config.enabled=false --server.port=8084
4 本机探测提醒 本机 Git Bash 设了 http_proxy=http://127.0.0.1:53624，直接 curl 127.0.0.1:<port> 会被代理拦成 502 假阳性。探测本地端口务必加 --noproxy '*'
