跨服务超时预算：登记表 + 门禁 + 生成型链路修复¶

项目: Agent-Lifeform | 日期: 2026-09-19 本轮范围: contracts/timeout-budget.yaml（新建）· scripts/timeout-budget-check.py（新建）· services/node/wp-bff/server.js（分档）· services/node/wp-bff/test/server.test.js（+6 用例）· scripts/start.sh（前置门禁） 触发：上一轮交付时留下的第 2 条优化建议 —— 「跨服务超时预算无人守：现在能看见是超时还是缺失，仍不能防新设的超时值再次小于对端最坏耗时」 代码基线：0921345（开工前已核对远端三分支无新提交）

1. 结论摘要¶

维度 落地前 落地后
超时值管理 一个默认值打天下（httpRequestJson 默认 5000ms）+ 1 处写死的 30000 按操作类型分 8 档，命名常量，WP_BFF_*_TIMEOUT_MS 可覆盖
倒挂是否可发现 不可发现（单测全绿、契约 0 FAIL） 权威登记表 19 条边 + 三层门禁，倒挂即 FAIL
生成型链路预算 5000ms（下游 LLM 级联最坏 22000ms） GENERATE 档 45000ms
数字与文档一致性 靠人工核对（台账「数字级门禁未落地」长期欠账） 锚点校验 + 魔法数字扫描，代码实值 ≠ 表中数字即 FAIL
检查时机 运行期事后发现 提交期门禁 + ./scripts/start.sh 前置自检

一句话：本轮把一个「靠人记得住」的隐性约束，变成了「忘了就红」的显性门禁。

2. 开工侦察：倒挂不是未来风险，而是现在就成立¶

先扫全仓所有跨服务超时值，起点状态（0921345）：

services/node/wp-bff/server.js
  L55   function httpRequestJson(url, { ..., timeoutMs = 5000 })   ← 默认值，几乎所有调用点都用它
  L1212 timeoutMs: 30000                                           ← 唯一一处显式值（知识入库）

即：BFF 的整个跨服务调用面，实质上只有两个数字。逐条比对下游最坏耗时后：

边 调用点 落地前预算 下游最坏 余量 判定
TB-04 POST /api/body/knowledge（入库） 30000（写死） 30000（嵌入读超时） 1.00x ❌ 余量 0
TB-05 GET /knowledge/stats、POST /body/retrieve 5000 10000 0.50x ❌ 小于下游
TB-06 POST /nlp/brain/ask 5000 22000 0.23x ❌ 严重倒挂
TB-07 memory/ingest、memory/compress 5000 22000 0.23x ❌ 严重倒挂
TB-09 POST /session/{id}/ask 5000 10000 0.50x ❌ 小于下游

下游 22000ms 的来源（app/brain/llm_gateway.py）：

_FALLBACK_ORDER = (L1, L2)                 # 级联顺序
_DEFAULT_TIMEOUTS = {L1: 3.0, L2: 8.0, L3: 20.0}
# max_retries = 1 → 每级最多 2 次
# 最坏 = L2 8s×2 + L1 3s×2 = 22s

关键点：这不只是「接入真实 LLM 后才会出的事」。即使只跑 TemplateEngine（L1）， 最坏 3s × 2 次 = 6s > 5000ms —— 也就是说，当前未配真实 LLM 的部署里，这条边已经倒挂， 只是模板引擎实际毫秒级返回，所以从未触发。这类缺陷的特征是 「纸面自洽、单测全绿，直到某次抖动才现形」。

3. 登记表：把「两个数字」放到同一行¶

新建 contracts/timeout-budget.yaml（权威副本），19 条边：

budget_tiers:            # wp-bff 按「操作类型」分档，不按端点硬编码
  READ: 5000             # 纯查询
  RETRIEVE: 15000        # 检索型（下游读超时 10s）
  GENERATE: 45000        # LLM 生成型（下游级联最坏 22s）
  WRITE: 60000           # 写入型
  EXECUTE: 60000         # 工具执行（沙箱）
  SANDBOX_PROBE: 9000    # 容器探测
  MIDDLEWARE_START: 180000
  MIDDLEWARE_STOP: 120000

每条边记录：调用方 / 被调方 / 操作 / 档位 / 上游预算 / 下游最坏耗时 / 耗时依据 / 代码锚点（文件 + 正则 + 缩放）/ 状态。例：

  - id: TB-06
    caller: wp-bff
    callee: nlp-service
    operation: "POST /api/nlp/brain/ask"
    tier: GENERATE
    upstream_budget_ms: 45000
    downstream_worst_case_ms: 22000
    downstream_basis: "LLM 级联最坏：L2 8s×2 次 + L1 3s×2 次（max_retries=1）"
    upstream_anchor_file: services/node/wp-bff/server.js
    upstream_anchor_pattern: "const GENERATE_TIMEOUT_MS = Number\(process\.env\.WP_BFF_GENERATE_TIMEOUT_MS \|\| (\d+)\)"
    status: ok

设计取舍（都在文件头部注释里写明）：

  • 余量比 1.5，不是 1.2。理由：跨服务还叠加网络往返、序列化、调度抖动； 实测沙箱那条曾经 1.4x 仍出过事，1.2 太紧。
  • 豁免两类边：docker 启停 watchdog（超时是解除中间态的兜底，不是失败）、 TCP 健康探针（超时 = 判定为 down，是预期结果）。豁免需显式写 exempt_headroom: true。
  • 推导值不假装成常量：LLM 级联的 22s 在代码里没有对应常量，故用 downstream_anchor_expected_ms: 3000 声明「锚点指向的是 L1 单级 3s」， 与表里的 22000ms 分开校验 —— 既防漂移，也不假装能自动推导。

4. 门禁：三层校验（scripts/timeout-budget-check.py）¶

python scripts/timeout-budget-check.py            # 默认：gap 仅列出，不算失败
python scripts/timeout-budget-check.py --strict   # 修复期：gap 也算失败
python scripts/timeout-budget-check.py --list     # 打印全表摘要（预算/余量/状态）
层 校验内容 防的是什么
① 语义 上游预算 ≥ 下游最坏 × 1.5 预算不足（倒挂）
② 锚点 按登记表声明的正则从真实代码提取实值，与表中数字比对 「表里写 A、代码是 B」的漂移
③ 魔法数字 扫调用点，禁止就地写数字 ②的盲区补丁（见下）

第 ③ 层的由来（本轮踩到的真实盲区）：②锚的是常量定义， 而缺陷可以藏在调用点。实测：POST /api/body/knowledge 调用点写 timeoutMs: 30000 （= 下游最坏，余量 0），而表里记的是常量 60000 —— 门禁全绿，缺陷仍在。 一个锚点写得再准，也管不住「有人绕过常量直接在调用点写数字」。

配套约定： - 仓内不引入 PyYAML 依赖（与 contract-check.py 同一路线），脚本自带行式解析器； 解析约定（条目保持扁平、引号内反斜杠按字面保留）写在脚本 docstring 与登记表头部。 - 一条坏正则不会让门禁崩溃，而是报 FAIL —— 避免重演「巡检脚本恰在故障时失效」（上一轮 healthcheck 的老毛病）。

5. 修复：生成型链路改用命名档位¶

services/node/wp-bff/server.js 新增档位常量，并逐处应用：

const READ_TIMEOUT_MS     = Number(process.env.WP_BFF_READ_TIMEOUT_MS     || 5000)
const RETRIEVE_TIMEOUT_MS = Number(process.env.WP_BFF_RETRIEVE_TIMEOUT_MS || 15000)
const GENERATE_TIMEOUT_MS = Number(process.env.WP_BFF_GENERATE_TIMEOUT_MS || 45000)
const WRITE_TIMEOUT_MS    = Number(process.env.WP_BFF_WRITE_TIMEOUT_MS    || 60000)
const EXECUTE_TIMEOUT_MS  = Number(process.env.WP_BFF_EXECUTE_TIMEOUT_MS  || 60000)
调用点 落地前 落地后 余量变化
POST /nlp/brain/ask 5000（默认） GENERATE 45000 0.23x → 2.05x
POST /session/{id}/ask 5000（默认） GENERATE 45000 0.50x → 4.50x
POST /brain/memory/ingest 5000（默认） GENERATE 45000 0.23x → 2.05x
GET /knowledge/stats（第 2 处） 5000（默认） RETRIEVE 15000 0.50x → 1.50x
POST /body/knowledge（入库） 30000 写死 WRITE 60000 1.00x → 2.00x

同时刻意不做的两件事：

  1. 不把读型端点一起拉长。把 session/stats 这类 Redis 单次往返也提到 45s， 会让真实故障等 45s 才暴露降级 —— 那是把「快速失败并降级」换成「长时间等待后仍降级」。 用例 读型端点必须保持短预算 显式守住这条。
  2. 不给所有档位用同一个值。用例 生成档与读型档必须真的分开 断言 gen.timeoutMs > read.timeoutMs —— 防的是「图省事把两档合并」。

6. 验证¶

6.1 新增回归用例（wp-bff，+6 条 → 87 / 0 失败）¶

用例 守的不变量
生成型链路（brain/ask）使用生成档预算 必须显式声明且 = GENERATE（不得依赖读型默认值）
生成型链路（session/{id}/ask）同样使用生成档 会话问答内部转调 LLM，同样受约束
生成型链路（memory/ingest）使用生成档 记忆抽取走 LLM
检索型链路（body retrieve）预算覆盖下游读超时 10s RETRIEVE 档 ≥ 下游读超时
读型端点必须保持短预算 防一刀切拉长（explicit === false 且 ≤ READ）
生成档与读型档必须真的分开 两档被合并立即失败

与门禁脚本互补，缺任一方都有盲区：

  • 脚本守「登记表数字 ↔ 代码常量」→ 防的是「表里写 A、代码是 B」；
  • 用例守「代码行为 ↔ 操作类型」→ 防的是「改了行为却忘了常量 / 分档被合并」。

用例断言一律用 TIMEOUT_TIERS 常量与下限/上限，不用精确字面值 —— 运维通过环境变量调档不会误伤用例。为此把档位以 TIMEOUT_TIERS 导出， 测试替身镜像生产默认值（否则读型调用录到 undefined，用例就只能断言「有没有传」， 而断言不了「档位对不对」—— 这正是首轮 5 条用例失败的原因）。

7. 遗留与建议¶

# 项 状态
1 GAP-01：session-manager 问答读超时 10s < LLM 级联 22s 登记未修（跨服务，属 P6 编排预算命题）
2 GAP-02：session→body 检索上游 = 下游读超时（余量 0） 登记未修
3 GAP-03 / GAP-04：body→nlp 嵌入、sense→nlp OCR 下游无独立超时 登记未修（需 Python 侧加超时，否则「覆盖」无法证明）
4 GAP-05：nlp→body 检索 5s < 下游 10s 登记未修（跨语言）
5 REC-01：LLM 级联缺总预算上限（deadline propagation） 建议项，P6 决策
6 REC-03：单服务内的线程池/队列等待同类错配未扫 建议项

根本方向（REC-01）：当前 max_retries=1 且逐级放宽超时（L1 3s → L2 8s → L3 20s）， 最坏耗时是「各级超时 × 重试次数」的乘积，随层级与重试数增长而膨胀。 正确做法是给一次 generate() 调用一个总 deadline，级联只在该 deadline 内调度 —— 这样上游预算才能可靠覆盖下游。否则只能靠不断调大上游超时， 而那会把「快速失败并降级」变成「长时间等待后仍降级」，损害体验且掩盖故障。

8. 认知沉淀¶

同一形状的缺陷，这一天出现了第四次：

# 场景 表现
1 沙箱探测慢 5.7s 被写成「沙箱不可用」
2 BFF 四种失败 塌缩成同一个 null
3 healthcheck 恰在「发现故障」这个动作上失败
4 知识入库调用点 写死 30000 = 下游最坏，门禁看不见

共同点：下游只拿到一个空值 / 一个裸数字，就丢失了全部可行动信息。 本轮的应对不是「再小心一点」，而是把约束搬到机器能检查的地方： 登记表让两个数字必须同框，门禁让不一致必须变红。

附带一条：门禁自身也会犯同样的错 —— 首版只锚常量定义， 对调用点的魔法数字视而不见。所以「加门禁」之后必须反向验证门禁有效， 否则只是多了一个绿着好看的东西。
