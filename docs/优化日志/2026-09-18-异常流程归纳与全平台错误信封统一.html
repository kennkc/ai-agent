1. 本轮目标¶

两件事，顺序不能反：

  1. 审核：判断当前开发进度与质量是否还有需要优化的地方 —— 不能只信门禁和阶段报告的结论；
  2. 归档：把本轮开发中归纳出的异常流程沉淀到文档，而不是留在对话里。

判定标准是可执行的：把「每个服务失败时到底吐什么」横向摆开对比，而不是逐个服务看它自不自洽。

2. 审核方法¶

手段 具体做法
跑全部门禁 Java / Python / wp-bff / 契约 / 文档覆盖 / 前端 —— 先确认"成功路径"没问题
跨服务横向比对 对同一组反例（未映射路由 / 存在但方法不符 / 错误 Content-Type / 坏请求体），逐个服务打一遍，横向对比响应形状与状态码
错误形状反查 grep -rn "res.json({ *error\|{error:" services/node/wp-bff/server.js；Java 看 GlobalExceptionHandler 落点；Python 看是否裸漏 FastAPI 默认体
覆盖范围盲区检查 检查各服务的 HTTP 层是否有对应测试（本轮发现 nlp-service 完全为零）

为什么需要"横向"比对：单服务测试永远只证明它自己自洽。 同一份 Phase 3 代码里，{code,message,details} / {error} / FastAPI 默认 detail 三种形状并存了很久， 而各自的门禁都是绿的 —— 直到把它们放在一起看才发现。

3. 审核结论：3 处真实缺口¶

# 缺口 危害 为什么门禁照不到
1 错误信封三种形状：Java {code,message,details} / wp-bff {error} / nlp-service 裸漏 FastAPI 默认体（detail） 客户端要写三套解析逻辑，前端 status.ts 无法统一登记状态徽标 契约只校验端点存在与否，不约束错误响应体形状
2 wp-bff 对"方法不支持"返回 404，而 Java 三服务返回 405 同名语义相反：把"用错方法"伪装成"端点不存在"，排查方向被直接带偏 单服务各自自洽；没有测试断言"同 vs 不同服务语义一致"
3 nlp-service HTTP 层零测试（52 项全在业务层） 异常映射改了没人拦 覆盖率统计按文件/包维度，看不出某一层没有测试

10. 关键教训¶

门禁全绿 ≠ 失败路径正确。

130 个用例、0 FAIL 契约、106/106 文档覆盖，全部只对成功路径设防； 本轮三处缺口无一例外藏在错误分支里。

推论：横切关注点（错误形状、鉴权口径、状态码语义）必须做"跨服务一致性"检查， 而不能靠单服务自己的测试 —— 单服务测试永远只证明它自己自洽。
