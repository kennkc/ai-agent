## 6. 标准部署流程

```bash
# 1. 环境检查
pwsh -File scripts/check-toolchain.ps1

# 2. 复制环境变量模板
cp .env.example .env

# 3. 启动基础设施
docker compose up -d

# 4. 验证基础设施
bash scripts/healthcheck.sh

# 5. 启动 Java 服务
cd services/java
mvn -B -ntp test

# 6. 启动 Python 服务
cd services/python/nlp-service
..\venv\Scripts\python.exe -m pytest -q

# 7. 安装并启动工作平台
cd web/work-platform
npm ci
npm run build
```

生产环境必须使用独立密钥管理系统，不得把 `.env`、模型 API Key、控制令牌或模型权重提交到 Git。

## 7. 维护约定

1. 升级 Java、Node、Python、镜像或前端依赖时，先修改清单文件，再修改本文档。
2. CI 必须执行 `check-toolchain` 所需的核心组件检查。
3. 安装指南中的路径以仓库实际结构为准，不复制第二份版本真值。
4. 外部模型 Key 只允许通过环境变量、CI Secret 或模型配置加密落库注入。

## 8. 后台服务监控与本地受控启停

工作平台新增 `后台服务` 页面，监控 8 个应用服务：

```text
gateway-service / session-manager / nlp-service / body-service
tool-executor / collab-bus / wp-bff / work-platform
```

控制面由 wp-bff 提供：

```text
GET  /api/wp/services
POST /api/wp/services/{key}/start
POST /api/wp/services/{key}/stop
```

安全边界：

1. 仅允许 `APP_SERVICES` 白名单中的 key；
2. 启动命令、参数、工作目录全部由服务端固定，不接受客户端命令；
3. 写路径仍经过 Origin 白名单 + `X-WP-Control-Token`；
4. `wp-bff` 自身只监控，不允许自停止；
5. 外部启动的进程无法安全推断 PID，`stop` 返回 409，不猜测、不误杀；
6. `WP_BFF_APP_CONTROL=false` 可关闭控制，只保留监控。
## 9. 生产反向代理与 BFF 路由

开发环境通过 Vite 代理访问 wp-bff；生产环境必须走统一入口：

```text
Nginx
  -> /              Vue dist 静态资源
  -> /api/**        gateway-service
  -> /api/wp/**     gateway-service -> WP_BFF_URI -> wp-bff
```

配置位置：

- `services/java/gateway-service/src/main/resources/application.yml`
  - `work-platform-bff` 路由：`Path=/api/wp/**`
  - 上游：`${WP_BFF_URI:http://127.0.0.1:8090}`
- `infra/nginx/lifeform.conf`
- `infra/nginx/README.md`

生产检查：

```bash
curl -fsS http://127.0.0.1/healthz
curl -fsS http://127.0.0.1/api/wp/healthz
```

第二个请求必须经过 gateway-service 到达 wp-bff，不得依赖 Vite 开发代理。

## 10. 模型配置生产 fail-closed

模型配置唯一主存储为 PostgreSQL `llm_model_config`。

| 变量 | 开发默认 | 生产要求 |
|---|---|---|
| `MODEL_CONFIG_MASTER_KEY` | 可退化为本地密钥文件 | 必须由密钥管理系统注入 |
| `MODEL_CONFIG_ALLOW_LOCAL_KEY_FILE` | `true` | 必须为 `false` |
| `MODEL_CONFIG_REQUIRE_PERSISTENCE` | `false` | 必须为 `true` |

生产设置 `MODEL_CONFIG_REQUIRE_PERSISTENCE=true` 后：

- PG 新增、更新、删除失败返回 `503 AGENT_CONFIG_STORAGE_UNAVAILABLE`；
- 不得写入进程内存储后返回成功；
- 本地密钥文件自动生成能力必须关闭；
- `status()` 返回 `persistence_required`、`key_available` 与 `key_source`，供观测页和告警判定。
## 11. Prometheus 与告警

基础设施：

```bash
docker compose up -d prometheus alertmanager
```

访问：

- Prometheus: `http://127.0.0.1:9090`
- Alertmanager: `http://127.0.0.1:19093`

抓取端点：

| 服务 | 路径 |
|---|---|
| Java 服务 | `/actuator/prometheus` |
| nlp-service | `/metrics` |
| wp-bff | `/metrics` |

告警规则位于 `infra/prometheus/alerts.yml`，当前包含：

- `LifeformTargetDown`
- `LifeformHighHttpP99`
- `LifeformHighJvmMemory`

`alertmanager.yml` 默认 receiver 不发送外部通知；生产部署必须替换为组织邮件、企业微信、Slack 或其他 webhook。
