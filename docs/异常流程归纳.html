1.2 各层的异常职责（不要跨层越权处理）¶

层 只负责 明确不做
gateway 认证/租户（401/403），转发 不实现 GlobalExceptionHandler，JwtAuthFilter.reject() 手写同格式 JSON
BFF 聚合、代理、写路径鉴权、路由层分流 不吞体层错误（体层错误码原样上报）
Java 三服务 业务异常 → 错误码 → HTTP，路由层分流 不伪造上游结果
nlp-service 算法与请求校验 不决定业务语义
前端 降级判定与可见化 不静默回落 Mock

2. 运行期异常流程¶

2.1 统一错误信封（全平台唯一格式）¶

所有错误响应都是 {code, message, details}（R1-08）。客户端只需一套解析逻辑。

服务 出处
gateway-service JwtAuthFilter.reject() 手写 JSON（WebFlux 不走 @ControllerAdvice）
session-manager / sense-service / body-service common/GlobalExceptionHandler + ErrorCode 枚举
wp-bff server.js → fail(req,res,status,code,message,details)
nlp-service app/main.py → 三个 @app.exception_handler

2.2 路由层分流：404 / 405 / 415（三种语义必须可区分）¶

为什么必须区分：前端据 404 判定「端点未实现（契约 x-wp-status: planned）」，据 5xx 判定「服务故障」。若未映射路由落进兜底 500，两者不可区分，前端既不能降级也不能报障。

情形 HTTP 错误码 响应头/明细
路径不存在 404 AGENT_NOT_FOUND Java details={}；BFF details={path}
路径存在、方法不支持 405 AGENT_METHOD_NOT_ALLOWED 必带 Allow 头；details={method, supported}
Content-Type 不支持 415 AGENT_BAD_REQUEST details={content_type}（Java 侧）
请求体不合法 400 AGENT_BAD_REQUEST details 为「字段 → 原因」映射

各服务实现落点

服务 机制
Java 三服务 @ExceptionHandler({NoResourceFoundException, NoHandlerFoundException}) → 404；HttpRequestMethodNotSupportedException → 405；HttpMediaTypeNotSupportedException → 415
wp-bff ROUTE_GUARD（由 IMPLEMENTED_ENDPOINTS 派生，不另立第三份端点真相）→ 命中路径但方法不符则 405 + Allow；否则 404
nlp-service StarletteHTTPException 统一处理器（透传框架的 Allow 头）；422 一律归并为 400，使状态码语义与 Java/BFF 一致

实测证据（2026-09-18，运行态）

探测 结果
GET 8083 /api/body/definitely-not-a-route 404 AGENT_NOT_FOUND
DELETE 8083 /api/body/knowledge 405 AGENT_METHOD_NOT_ALLOWED，details.supported=[POST, GET]
POST 8083 /api/body/rag/answer + text/plain 415 AGENT_BAD_REQUEST
GET 8090 /api/wp/not-exist 404 AGENT_NOT_FOUND，details={path}
GET 8090 /api/wp/knowledge/search 405 + Allow: POST
GET 8090 /api/wp/middleware/redis/start 405 + Allow: POST（参数化路径同样覆盖）
GET 8000 /api/nlp/not-exist 404 AGENT_NOT_FOUND
GET 8000 /api/nlp/embed 405 + allow: POST
POST 8000 /api/nlp/embed {"texts":"abc"} 400 details={texts: Input should be a valid list}

2.3 信封不一致的历史（三个形状 → 一个）¶

服务 2026-09-18 之前 现在
Java 三服务 / gateway {code,message,details} 不变（基准）
wp-bff {error: "..."} ✅ 已统一
nlp-service FastAPI 默认 {detail: ...} ✅ 已统一

行为变更提示：任何解析 BFF 旧 error 字段的外部消费方需改读 message。仓库内消费方已全部核对：前端只读 HTTP 状态码（error.response.status），4 处旧断言已改写为断言 code/message。

规范性结论：新增服务的错误出口必须沿用该信封，07-运行时配置与横切约定 §5 已有明文约定。

2.4 鉴权异常流程（401 / 403）¶

触发 HTTP 错误码 硬约束
无 / 非法 Bearer（gateway） 401 AGENT_UNAUTHORIZED —
JWT 缺 tenant_id（gateway） 403 AGENT_FORBIDDEN —
BFF 控制端点无令牌 / 令牌错 401 AGENT_UNAUTHORIZED 不触达下游
BFF 写路径来源不在白名单 403 AGENT_FORBIDDEN 不触达下游（CSRF 防护）

判定的核心不变量：鉴权必须按「方法」判定，不能按「路径」判定。 GET /api/wp/knowledge 免令牌（只读），但 POST（写）必须与 /middleware/{key}/start|stop 同级校验。反向用例必须断言「鉴权失败时下游零调用」——否则写成 assert status==401 却漏了后门。

实测：无令牌 401、伪造 Origin 403，且测试断言 jsonRequest 未被调用。

2.5 降级链路（逐服务）¶

① session-manager —— 上游不可用时的业务降级

上游 降级行为 开关
nlp-service 意图识别退化为 FALLBACK（intent=闲聊, confidence=0.5, engine=FALLBACK），让问答链路继续走模板回答而非整链路 503 app.nlp.degrade-on-failure（默认 true）
body-service 检索退化为空结果 app.body.degrade-on-failure（默认 true）

关掉开关 → 抛 BizException(AGENT_UPSTREAM_UNAVAILABLE) → 502。

② body-service —— 上游引擎缺失时的确定性降级

能力 缺失时 标记
嵌入 回落 hash-ngram-768 确定性后端（DEBT-010） degraded=true
重排 回落 lexical-coverage 词法打分（DEBT-011） degraded=true

入库失败不留半成品：文档状态机 PENDING → INDEXED，异常时写 FAILED 并把原因截断落库后原样抛出（不吞错、不假装成功）。 重排不可用不阻断检索（保留召回顺序 + log.warn）。

③ sense-service —— 渠道级自愈

渠道故障 → 健康监控自动隔离 → 路由降级到候选渠道 → 指数退避重试（默认 maxAttempts=3）→ 重试耗尽入死信（DeadLetterStore）。

④ wp-bff —— 体层不可用时的「可用性信封」（设计取舍，非缺陷）

体层不可用/被拒时返回 HTTP 200 + {available:false, reason, error_code?}，而不是 5xx。理由：对知识视图而言「体层不可用」是一种要展示的状态（页面渲染「体层不可用」标签），且需保持响应体结构统一。

已知代价：监控无法仅凭状态码区分该情形，需读 available 字段。若要按状态码告警，需改为 502 并在前端同步调整——当前不改，如实登记为取舍。

⑤ 前端 —— 降级必须可见

status.ts 的 reportDegrade(scope, reason) / reportApiOk(scope)：失败即登记，成功即清除；顶栏徽标 API · 降级 N + 全局横幅 + 逐模块提示。

  • 读端点：可回落演示数据，但必须登记降级 + 页面标注「演示数据」
  • 写端点：一律走 plannedEndpointError() —— 登记降级 + 抛说明性错误，绝不伪造成功
  • 视图层 retry/apply 类动作全部 try/catch，失败不改本地状态

⑥ tool-executor —— 沙箱真隔离不可用时的显式降级（Phase 5）

能力 缺失/不可用时 标记 是否伪实现
Docker 沙箱 回落 RestrictedProcessBackend（受限子进程，非真隔离） active_backend=process-restricted + degraded=true + isolated=false ❌ 否 —— 降级可见，GET /api/tool/sandbox 如实上报
审计落 PG 回落进程内审计 audit_backend=in-memory + degraded=true ❌ 否
工具注册表 进程内（重启丢失） registry_backend=in-memory（DEBT-019） ❌ 否
工具决策（Python 侧） 规则决策 decider="rule" ❌ 否

工具执行失败（超时 / 非零退出 / 沙箱拒绝）一律返回 success:false + 真实错误码（见 07-运行时配置与横切约定.md §5.2）， 信封 details 带 call_id / audit_id；连续失败 3 次触发熔断 30s（AGENT_TOOL_CIRCUIT_OPEN），不静默返回空结果。 BFF /api/wp/tools* 在 tool-executor 不可达时回 200 + available=false + gaps（与体层同一「可用性信封」约定）。

⑦ BFF 子请求失败：四类原因必须可区分（Phase 5 · 2026-09-19 加固）

BFF 聚合多分支时，子请求失败不再统一塌缩为 null，而是携带原因码：

reason 语义 运维动作 若曾合并会怎样
timeout 对端在预算内未返回（冷启动 / 负载高） 重试通常即恢复 被读成"服务不可用" → 白重启服务
unreachable 连接被拒 / DNS 失败 查进程与端口 同上
endpoint_missing（HTTP 404） 端点不存在 —— 版本不匹配的强信号 升级对端服务 被读成"不可用" → 白排查网络
http_error / bad_json 对端 5xx / 返回非 JSON 查对端日志 无区分度

分片缺失码随之外带后缀：sandbox_timeout（慢）/ sandbox_missing（版本旧）/ sandbox_unavailable（真连不上）。 响应同时给出 partial_note（人类可读解释）与 probe_budget_ms（各子请求预算，排查"慢 vs 没有"用）。 前端 ExecutionView.vue 必须把码翻成人话，不得直接把 raw code 打到用户界面。

教训：沙箱冷探测 5.7s 超出 BFF 工具域 5.0s 预算（余量仅 0.7s）时，工具域曾把"慢"叙述成"沙箱不可用"—— 与服务侧真相恰好相反，且不影响任何功能断言，单测全绿、契约 0 FAIL，只表现为静默降级。 凡返回 null / false / 空数组的位置，都要问一句「调用方还能区分出哪几种情况」。

2.6 planned 端点：三态判定¶

状态码 语义 前端动作
2xx 正常（含 BFF 的 available=false 可用性信封） 直接用，读 available 判降级
404 契约 x-wp-status: planned，本阶段不提供 登记降级 → 展示演示数据或禁用入口
400 / 401 / 403 / 405 / 415 客户端用错（参数/凭据/方法/媒体类型） 报错并上抛，不得静默降级
5xx 服务故障 登记降级 + 报障

x-wp-status: planned 的端点在第 2.5 ④ 与本节共同约束下，不会出现「静默拿 Mock 冒充真实结果」。

2.7 异常处置决策树（排障用）¶

现象
├─ 拿到 404？
│   ├─ 该路径在契约里是 planned ──────────→ 正常，前端走降级展示
│   └─ 契约里是 implemented ─────────────→ 真问题：查路由是否注册（@PostMapping / 检查 ROUTE_GUARD 派生）
├─ 拿到 405？ ────────────────────────────→ 客户端方法用错，看 Allow 头自纠；若 Allow 与预期不符 → 契约与实现不一致
├─ 拿到 415？ ────────────────────────────→ Content-Type 必须是 application/json
├─ 拿到 401 / 403？
│   ├─ 直连 8090 写路径 ─────────────────→ 预期行为（令牌由 Vite 代理注入，浏览器直连必然 401）
│   └─ 经代理仍 401 ────────────────────→ 令牌文件与进程不一致（重启后令牌会重新生成）
├─ 拿到 502 / 503？ ─────────────────────→ 上游不可用：看该链路的 degrade-on-failure 开关与上游健康
├─ 拿到 500？ ──────────────────────────→ 兜底分支。**只记日志、不回内部消息**；查服务日志 "Unhandled exception"
└─ 200 但数据不对？ ────────────────────→ 读 available / degraded / data_source 三个字段，别只看状态码

3. 研发期异常流程（过程性，D 组）¶

编排原则：这一类异常不产生业务代码，却反复消耗时间。归纳成「现象 → 根因 → 规范动作」，可直接前置检查。

编号约定：D-xx 按新增时间递增，与章节顺序不同步 —— 后续轮次新增的条目挂到所属类目下、取当时的下一个空号。 因此出现「3.2 里是 D-31/D-32、3.3 里是 D-33~D-35、3.4 里却是 D-13~D-16」这类顺序跳变是预期行为。 唯一硬约束：编号全局唯一（新增条目前先 grep -o '^| D-[0-9]*' | sort | uniq -d 确认无撞号）。

3.3 超时预算类¶

这一类的共同点：缺陷只存在于两个数字的差值里，两侧各自看都"没问题"，单测全绿、契约 0 FAIL。
