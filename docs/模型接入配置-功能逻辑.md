# 模型接入配置（WB-10）· 功能逻辑说明

> **口径时间**：2026-09-20 · **代码基线**：Phase 5 收口线 + WB-10 落地 + OpenRouter 外部 E2E 验证
> **需求源**：`AGENT_CONTEXT/WB-功能融入/WB-P5-需求设计文档.md`（WB-10 模型策略可视化管理 + Token 用量看板）
> 本文件回答一个问题：**在前台把一个模型配上去，到它真正被某次问答调用，中间到底发生了什么？**
>
> 与相邻文档的分工：`功能开发流程.md` 讲"这类功能该怎么开发"；本文件讲"这个功能现在是怎么运转的"；
> `异常流程归纳.md` 讲"出错时每一层回什么"；`../db/postgres/schema.md` 讲"表长什么样"。

## 一、要解决的问题

> **OpenRouter 兼容说明（2026-09-20）**：`openai` / `deepseek` / `qwen` 以及新增的 `openrouter` 均为 OpenAI 兼容供应商；`openrouter` 默认 Base URL 为 `https://openrouter.ai/api/v1`。可先用 `custom` 配置，也可直接选择 `openrouter`。

改造前，「换一个模型」这件事要走完 `改 .env → 重启服务 → 祈祷环境变量没写错` 三步。
这不是四个独立的小痛点，而是同一个根因的四种表现：

| # | 现象 | 根因 | 本模块的处置 |
|---|---|---|---|
| 1 | 换个模型要重启进程 | 配置住在**环境变量**里，进程启动时读一次 | 配置搬进 PG 表 `llm_model_config`，前台可增删改查 |
| 2 | 意图分类和长文生成被迫用同一个模型 | 配置维度是"**哪个服务调**"，而一个服务里混着多种任务 | 改成按"**这个活由谁干**"绑定 —— 功能角色 |
| 3 | API Key 明文躺在配置里 | 没有凭据落库的加密设计 | AES-256-GCM 加密落库，对外只回 `sk-***last4` |
| 4 | "我改了但好像没生效"无法判断 | 没有"当前实际装配了哪些引擎"的观测面 | `reload` 端点 + `role_summary()` 如实回报装配结果 |

## 二、分层与唯一真相源

一条配置从表到模型，要穿过四层。**每层只做一件事，且都不重复持有真相。**

```text
┌──────────────────────────────────────────────────────────────────────┐
│  前端  ModelsView.vue + provider.ts                                  │
│  职责：表单、按角色分组展示、显式降级标注                              │
│  不做：不持有默认值真相、不拼 base_url、不回填明文密钥                 │
└────────────────────────────┬─────────────────────────────────────────┘
                             │ /api/wp/models*（Vite 代理注入 X-WP-Control-Token）
┌────────────────────────────▼─────────────────────────────────────────┐
│  wp-bff  services/node/wp-bff/server.js                              │
│  职责：鉴权（写路径）· 透传 X-Tenant-Id · 4xx 信封原样透出 · 审计     │
│  不做：不连数据库、不校验业务字段、不缓存配置                          │
└────────────────────────────┬─────────────────────────────────────────┘
                             │ /api/nlp/models*
┌────────────────────────────▼─────────────────────────────────────────┐
│  nlp-service  app/main.py  ←→  app/model_config.py【唯一真相源】      │
│  职责：校验 · 加解密 · CRUD · 解析出引擎规格 · 探测连通性              │
│  不做：不决定"谁被调用" —— 那只属于 LlmGateway                        │
└────────────────────────────┬─────────────────────────────────────────┘
                             │ resolve_engines() 解密后的规格
┌────────────────────────────▼─────────────────────────────────────────┐
│  LlmGateway  app/brain/llm_gateway.py                                │
│  职责：把规格组装成角色引擎池 · 按角色优先 / 层级兜底选候选            │
│  不做：不读表、不碰密文（拿到的是已解密的规格）                        │
└──────────────────────────────────────────────────────────────────────┘
```

**唯一真相源 = PostgreSQL `llm_model_config` 表。**
BFF **没有**第二份配置副本（它是零依赖纯 Node 代理，不带 DB 客户端），
前端也**没有**内置的"默认模型清单"可回落到 —— 这是刻意的：
多一份副本就多一处会漂移的真相。

## 三、数据模型

见 `../db/postgres/schema.sql`。23 个字段，按用途分五组：

| 组 | 字段 | 说明 |
|---|---|---|
| **标识** | `id` · `tenant_id` · `config_key` · `name` | `config_key` = 功能角色（见 §5）；`name` 是人看的标签 |
| **接入点** | `provider` · `base_url` · `model` | `provider` 只影响表单预填默认地址，**不参与运行**（见下） |
| **凭据** | `api_key_cipher` · `api_key_hint` | 密文 + 掩码，**没有明文列**（见 §4） |
| **运行参数** | `tier` · `max_tokens` · `temperature` · `timeout_ms` · `routing_weight` · `enabled` | 逐条配置的超时是**这一条配置自己的预算**，不是全局 |
| **探测留痕** | `last_probe_at` · `last_probe_ok` · `last_probe_latency_ms` · `last_probe_error` | 最后一次连通性探测的结果，给界面显示"上次探活"用 |
| **审计** | `created_at` · `updated_at` · `updated_by` · `extra` | `updated_by` 取自请求身份，便于追责 |

**两条硬约束**（都与"结果不确定"有关，不是洁癖）：

1. `uq_llm_model_config_tenant_role_name (tenant_id, config_key, name)`
   —— 防"同一角色下配了两条同名模型"导致路由结果随插入顺序漂移。
   撞名时返回 **409 `AGENT_CONFLICT`**，前端据此给出可行动提示而不是笼统失败。
2. `idx_llm_model_config_tenant_role (tenant_id, config_key, enabled)`
   —— `resolve_engines()` 的查询形状就是"按租户 + 角色筛 enabled"。

> **`provider` 为什么不参与运行**：因为运行只需要 `base_url + model + api_key` 三件事。
> 若让 `provider` 参与路由决策，就会出现"改了 provider 名字但地址没变、行为却变了"的迷惑现象。
> `PROVIDER_DEFAULT_BASE_URL` 只在表单里做预填，**前端预填的东西在提交前是可改的**。

## 四、凭据安全（AES-256-GCM）

### 4.1 主密钥来源链（有优先级，且可追溯）

```text
① env  MODEL_CONFIG_MASTER_KEY        ← 生产必须走这条
   ↓ 缺失
② file MODEL_CONFIG_KEY_FILE          ← 默认 <nlp-service>/.model-config-key（0600，已 gitignore）
   ↓ 缺失则首次生成并落盘
```

`status()` 里的 `key_source` 会回报**当前实际用的是哪一条**；
走文件时会附带 `key_source_warning`（"仅限开发环境"）——
让"生产环境忘了配主密钥"这件事在界面上就能看见。

> **刻意不做**"每次启动随机生成一个密钥"。那看起来很安全，实际会让上次存的密文
> 在重启后静默变成一堆不可解字节 —— 表现为"重启后模型全部不可用"，且没有任何明文线索。

### 4.2 加解密口径

| 项 | 值 |
|---|---|
| 算法 | AES-256-GCM（认证加密，密文被篡改会解密失败而非静默返回垃圾） |
| AAD | `b"lifeform.llm_model_config.v1"` —— 把**格式版本**绑进认证范围，将来换格式不会与旧密文混淆 |
| 存储 | base64 密文 → `api_key_cipher`（TEXT） |
| 解密时机 | **只在构造引擎的那一刻**（`resolve_engines()`），不经手任何响应体 |

### 4.3 三条不变量

1. **对外接口永不回明文**：`GET /api/nlp/models` 的返回体里只有 `api_key_hint` 与 `has_api_key`。
2. **前端永不回填明文**：编辑弹窗里密钥框是空的。UI 上写明了理由 ——
   *"这里不会回填明文 —— 不回填才说明库里存的是密文"*。
3. **失败要分类，不能一律静默降级**：
   - 角色没配模型 → 回落 `TemplateEngine` 并标 `degraded`（**可接受**，service 不该因此不可用）
   - 凭据加解密失败 → **拒绝写入**（**不可接受**静默——那会让用户以为存进去了）

### 4.4 局部更新的密钥三态

`update_config()` 用"字段是否出现"区分三种意图，避免"改个超时把密钥清了"：

| 传入 | 行为 |
|---|---|
| 字段**未出现**（`None`） | 保持原密文与原掩码不动 |
| 传空串 `""` | **显式清空**凭据 |
| 传非空值 | 重新加密并覆盖 |

前端的对应交互：留空 = 保持；输入新值 = 轮换；输入单个空格后再清空 = 清除。

## 五、功能角色与引擎装配

### 5.1 六个角色

| key | 标签 | 默认层级 | 默认超时 | 用于 |
|---|---|---|---|---|
| `intent` | 意图识别 | L1 | 3000 ms | 会话入口的意图分类（量小、要求快） |
| `embed` | 向量嵌入 | L1 | 12000 ms | 知识入库与检索的向量化 |
| `rerank` | 检索重排 | L1 | 10000 ms | 检索结果重排 |
| `generate` | 内容生成 | L2 | 20000 ms | 问答与摘要的自然语言生成 |
| `plan` | 复杂规划 | L3 | 20000 ms | 多步任务拆解（Phase 6 小脑期） |
| `code` | 代码生成 | L2 | 20000 ms | 代码类工具调用 |

**为什么按角色而不是按服务**：`nlp-service` 一个进程里既有**意图分类**（要快、欢迎小模型）
又有**长文生成**（要长上下文、欢迎大模型）。按服务分粒度太粗，
只能给整个服务配一个模型，等于把痛点 #2 原样保留。

### 5.2 从表到引擎的装配规则

```text
llm_model_config 行
  → resolve_engines()   筛 enabled + base_url + model 齐全，按 routing_weight 降序，解密凭据
  → apply_specs()       逐条 HttpLlmEngine.from_spec()，**丢弃 available() 为假的**
  → gateway.role_engines: { role → [engine, engine, ...] }   ← 顺序即降级顺序
```

三条值得单独说的设计：

- **`available()` 为假的规格被丢弃，而不是注册成"永远不可用的引擎"。**
  后者会让 `health()` 报出的引擎数与实际能用的对不上，制造一个查不出原因的差异。
  对应地，`create_config`/`update_config` 都有一条硬校验：
  **`enabled=true` 必须同时提供 `base_url` 与 `model`** ——
  把"启用了但没地址"这种配置挡在写入期，而不是留到运行期表现为"引擎不可用"。
- **`routing_weight` 决定同角色内多模型的优先级**，不是数组顺序。
  这样"临时把某条调低"不需要删了重加。
- **`resolve_engines()` 只解密，不判断可用性**；可用性判定在网关侧。

### 5.3 真实调用时的候选序列：角色优先，层级兜底

`LlmGateway._candidates(request)` 的产出顺序**就是降级顺序**：

```text
① request.role 对应的角色引擎（按 routing_weight 顺序）
        ↓ 全部失败
② 原有层级级联 _fallback_chain(request.level)（L2 超时 → L1 重试 → 模板兜底）
```

**这一条是本功能与既有系统的接缝，也是最容易被改坏的地方。**
角色路由是**新增的一层前置**，它不能绕过原有的层级降级语义 ——
否则"角色模型挂了"会直接从"用配置的模型"跌到"没有回答"，而不是跌到层级兜底。
`_candidates()` 用 `seen` 集合去重，保证同一个引擎不会在序列里出现两次。

## 六、三条关键时序

### 6.1 保存一条配置（写路径）

```text
前端表单 → provider.saveModel()
   │  mock 数据源 → 直接拒绝（不伪造成功）
   ▼
POST /api/wp/models            （新建） 或  PATCH /api/wp/models/{id}（更新）
   ▼
wp-bff modelsWrite()
   ① 来源白名单（WP_BFF_ALLOWED_ORIGINS）→ 不通过 403 + 审计 REJECT_AUTH
   ② X-WP-Control-Token（timingSafeEqual）→ 缺失/错 401 + 审计 REJECT_AUTH
   │  ★ 鉴权失败**不触达下游**（有反向用例守着）
   ▼
nlp-service model_config.create_config() / update_config()
   校验角色 / 名称非空 / provider 合法 / tier 合法 / 数值区间
   enabled 必须齐备 base_url + model
   同角色内重名 → 409 AGENT_CONFLICT
   api_key → seal_secret() → api_key_cipher + api_key_hint
   ▼
PG upsert（失败则进程内存储 + degraded=True）
   ▼
返回 _to_public(row) + 附带 reload 摘要
   ▼
前端：reload.ok === false 时弹"配置已保存，但引擎重载失败……配置在库中，
      重启服务或点「重载引擎」后生效"  ← 不谎报成功，也不谎报失败
```

> **4xx 响应体必须原样透出**：BFF 用 `httpRequestJsonDetailed()` 而非普通 `httpRequestJson()`，
> 就是为了让 409 的 `{code:AGENT_CONFLICT, message, details}` 完整到达前端。
> 若在上游处把 4xx 吞成通用 500，前端就失去了"哪一个字段冲突"的信息。

### 6.2 重载引擎（不重启进程）

```text
POST /api/nlp/models/reload  →  LlmGateway.reload_from_model_config(tenant)
   → resolve_engines()  读表 + 解密
        └ 读取失败 → **保留原有装配**，返回 {ok:false, kept_previous:true, error}
   → apply_specs() 重建角色引擎池
   → 返回 {ok:true, count, roles:{role:[{name,model,level,timeout_ms,provider}]}}
```

**"读取失败保留原装配"是一条硬约定**：一次瞬时读表失败，不应该让线上问答
从"用配置好的模型"跌成"全部降级到模板"。宁可继续用稍微过期的旧装配，也不清空。

> 注：`POST /models/reload` 是**固定段**，必须排在参数路由 `/models/{model_id}` 之前。
> 这与 `/tools/{name}` 是同一类陷阱。BFF 用 `MODEL_RESERVED_SEGMENTS`
> **从 `IMPLEMENTED_ENDPOINTS` 派生**保留段清单，不另立第三份真相。

### 6.3 一次真实生成（读路径 + 降级链）

```text
会话请求 → LlmGateway.generate(request, deadline_ms)
   → _candidates(request)：角色引擎 → 层级级联
   → 逐个尝试，任一成功即返回
   → 全部失败 → TemplateEngine 兜底，响应标 degraded=True
```

## 七、wp-bff 代理层与安全边界

### 7.1 端点清单（6 条，全部登记进 `IMPLEMENTED_ENDPOINTS`）

| 方法 | 路径 | 鉴权 | 档位 |
|---|---|---|---|
| `GET` | `/api/wp/models` | 只读，免控制令牌（需 `X-Tenant-Id`） | `READ` |
| `POST` | `/api/wp/models` | 写路径，**白名单 + 控制令牌** | `WRITE` |
| `POST` | `/api/wp/models/reload` | 写路径 | `WRITE` |
| `PATCH` | `/api/wp/models/{model_id}` | 写路径 | `WRITE` |
| `DELETE` | `/api/wp/models/{model_id}` | 写路径 | `WRITE` |
| `POST` | `/api/wp/models/{model_id}/test` | 写路径 | `MODEL_PROBE` |

**鉴权按"方法"判定，不按"路径"** —— 这是本仓复审沉淀的硬规则。
`GET /models` 是只读所以免令牌，但**同一路径上的 POST 会真实改配置**，
必须与 `/middleware/{key}/start|stop` 同级校验。历史上正是因为沿用"这个路径是只读的"豁免，
短暂出现过无鉴权写入面。

### 7.2 BFF 不做的事

- **不连 DB**：BFF 是零依赖纯 Node 代理；DB 归属仍在 nlp-service。
  （否则会出现第二份 PG 连接配置，两处 DSN 迟早不一致。）
- **不校验业务字段**：`role` 合法性、数值区间等只在 nlp-service 判一次。
  BFF 只做"形状"层面的搬运。
- **不缓存配置**：避免"前台改完、BFF 还回旧值"的时序混淆。

### 7.3 审计事件

| 事件 | 触发 |
|---|---|
| `MODEL_WRITE` | 写路径成功（含 `HTTP <status>`） |
| `MODEL_REJECT` | 上游以 4xx 拒绝 |
| `MODEL_FAIL` | 上游不可达 / 异常 |
| `MODEL_DOWN` | 读路径降级（大脑层不可达） |
| `REJECT_AUTH` | 来源或令牌校验失败 |

## 八、前端（`ModelsView.vue`）

- **独立视图**，不再挂在 `ModuleView.vue` 的通用模块模板下。
  原因：`/models` 的返回结构已从"某个模块的运行态"变成"一份配置清单"
  （`{items, by_role, roles, providers, storage}`），形状对不上了。
  同时从 `getWorkbenchData()` 的聚合端点里移除了 `/models`，避免两种语义并存。
- **按功能角色分组渲染**配置卡片：启用开关 / 编辑 / 探测 / 删除；新建与编辑共用一个弹窗。
- **运行态观测区单独标注**：`ManagedModel` / `ModelRoute` / `ModelTokenTrend`
  这几个数据域 BFF **尚未提供接口**，界面显式打上
  `演示数据（BFF 未提供该数据域）` 标签 —— 配置是真的，运行态看板目前是示例。
  （WB-10 需求含"Token 用量看板"，该部分仍是演示数据，见 §11。）
- **写路径不伪造成功**：`saveModel` / `deleteModel` / `testModel` / `reloadModels`
  在 mock 数据源下直接拒绝；对 BFF 的 4xx 信封映射成可行动的中文提示。
- **探测结果口径**：`supported:false` 表示"该供应商不提供 `GET /models` 探测路径"，
  **不等于**"连接失败"。前端分开渲染这两件事。

## 九、降级与失败分类矩阵

| 场景 | 表现 | 是否可接受 | 依据 |
|---|---|---|---|
| PG 不可用 | `status().degraded=true`, `backend='memory'`；配置"改得动、重启即丢" | 可接受，但**必须显示** | 界面 + `status()` 如实回报 |
| `MODEL_CONFIG_MASTER_KEY` 未设 | 退回本地密钥文件并带 `key_source_warning` | 开发可接受 | 生产需注意 |
| 角色未配任何模型 | 该角色走层级级联，最终 `degraded=True` | 可接受 | 服务不因未配置而不可用 |
| 凭据加解密失败 | **拒绝写入** | 不可接受静默 | 静默会让人以为已存 |
| 上游 4xx（如 409 重名） | BFF 原样透出信封 | — | 保住"哪个字段冲突"的信息 |
| 上游不可达（写） | 503 | — | 不伪造成功 |
| 上游不可达（读 `/models`） | 200 + `available:false` | — | 界面可渲染"当前读不到配置" |
| 供应商无 `/models` 探测路径 | `supported:false` | — | 不把"探测方式不适用"说成"连不上" |
| 配置启用但缺 `base_url`/`model` | **写入期 400 拒绝** | — | 挡在写入期，不留到运行期 |

## 十、验收与测试覆盖

### 本轮顺带修复的既有缺陷

- **`llm_model_config` 主键分配错位（P1，会造成"配置静默丢失"）**：
  `id` 原先取自**进程内计数器** `_next_id()`，每次进程启动从 1 开始重算。
  只要库里已有行（服务重启后 / 多实例 / 残留数据），新建配置就必然撞
  `llm_model_config_pkey`；插入失败后只 `logger.warning` 一句就降级到进程内存储 ——
  **界面显示"保存成功"，重启后配置消失**。
  更隐蔽的是同一原因还会让 `BIGSERIAL` 序列长期落后于 `MAX(id)`
  （实测：表里已有 `id=10`，序列停在 `1`），因为旧代码**总是显式带 `id` 插入，从不推进序列**。

  修复：`_insert()` 改为 **`INSERT ... RETURNING id`，id 由 PostgreSQL 序列分配**；
  进程内计数器降级为"PG 不可用时的兜底"，并跳过已占用号；
  DDL 增加一条幂等的序列校正语句，把历史漂移一次性对齐。

- **`pg.ensure_schema()` 多处调用短路（真实隐藏缺陷）**：
  修复前该函数在**首次调用**后就靠 `_state['initialized']` 短路返回，
  于是"谁先调用，谁的 DDL 生效"。实测库中确实**缺 `memory_entity` / `memory_relation`**，
  而 `memory_graph` 的写入一直静默降级到进程内存储 —— 表面上只是"降级"，
  实际是"表根本没建"。改为按**语句集合**去重（所有 DDL 都是 `IF NOT EXISTS`，重复执行安全）。

- **`LlmEngine` 基类缺 `model` / `provider` 属性**：
  `role_summary()` 遍历角色引擎时，遇到非 `HttpLlmEngine` 的实现（如测试用的 `_FixedEngine`）
  会 `AttributeError`。已在基类补上默认属性并改用 `getattr` 取值。

- **测试隔离失效（缺 `tests/conftest.py`）**：
  `test_model_config.py` 原本在文件顶部用 `os.environ.setdefault("BRAIN_PG_ENABLED", "false")`
  声明"不依赖真实 PostgreSQL"，但这句**永远晚一步** ——
  `pg.py` 在导入期就把该变量读成常量，而 pytest 按文件名字典序收集，
  `test_brain.py` 先于它导入 `pg`。结果是测试**实际连上了真实库**：
  既污染开发库（实测留下 `test-*` / `enc-test` 等 8 行），
  又让结果依赖"库里当时有没有残留数据"。
  修复：新建 `tests/conftest.py` 在任何 `app.*` 导入之前钉死环境，
  并补 3 项回归用例守住 PG 路径的 SQL 形状与 id 分配语义。
