07 · 运行时配置与横切约定¶

本文汇总五个 Java 服务的配置、端口、环境变量，以及跨模块的横切约定 （多租户、错误码、观测、消息主题、HTTP 客户端）。部署、联调、排障时看这一篇。

1. 端口与实例对照¶

服务 HTTP gRPC Nacos 服务名 声明位置
gateway-service 8080 9091 gateway-service 各自 application.yml
session-manager 8081 19092 session-manager 同上
sense-service 8082 9093 sense-service 同上
body-service 8083 9094 body-service 同上
tool-executor 8084 9095 tool-executor 同上（Phase 5 新增）
nlp-service（Python） 8000 — nlp-service FastAPI 配置
wp-bff（Node，中间件观测 + 工作平台 BFF） 8090 — 未注册 Nacos services/node/wp-bff

gRPC 端口目前只提供 Health 服务（见 §5），业务 gRPC 尚未启用，因此端口占用不是部署瓶颈。

端口全部可在 application.yml 中通过 GRPC_PORT 等环境变量覆盖； HTTP 端口是写死的字面值（如 server.port: 8082），没有做环境变量占位 —— 多实例部署时需要另行处理。

4. 多租户契约（最关键的横切约定）¶

数据流：JWT 声明里的 tenant_id → 网关注入请求头 X-Tenant-Id → 各业务服务从请求头读取。

环节 责任 实现位置
令牌签发 把 tenant_id 写入 JWT 自定义声明 gateway/security/JwtService.sign
身份校验 + 注入 解析令牌，覆写 X-Tenant-Id 请求头 gateway/security/JwtAuthFilter
业务读取 只信任请求头，忽略请求体内同名字段 各 Controller 的 @RequestHeader("X-Tenant-Id")
数据隔离 会话/暂存/知识均按租户分区 SessionController.requireOwnedSession、BodyStore.tenantChunks、StagingStore

三条不可违反的规则：

  1. 业务服务不得信任请求参数里的租户 ID。sense-service 的 SenseController.collect 从请求体收到 tenant_id 也会忽略，只用请求头的值（见 05-sense-service §5.5）。
  2. 按 ID 访问租户资源必须校验归属。SessionController 的 requireOwnedSession 返回 403 而非 404（明确告知无权访问）。新增接口必须复用该模式。
  3. defaultValue = "default" 是个隐患。所有 @RequestHeader("X-Tenant-Id") 都带默认值， 因此绕过网关直连服务时，请求会自动落入 default 租户而不报错。 开发期方便，生产环境应确保业务服务端口不对外暴露，或考虑移除默认值。

5.1 路由层异常分流（2026-09-18 新增，三服务同源）¶

GlobalExceptionHandler 除了业务异常，还必须为路由层三类异常单独映射—— 它们不经过任何控制器，若落进兜底 @ExceptionHandler(Exception.class) 会返回 500， 使「调用姿势不对」与「服务真的坏了」在客户端不可区分：

触发场景 Spring 异常 返回 details
路径不存在（无控制器匹配） NoResourceFoundException（Boot 3.2+）/ NoHandlerFoundException 404 AGENT_NOT_FOUND path
路径存在但方法不对 HttpRequestMethodNotSupportedException 405 AGENT_METHOD_NOT_ALLOWED method / supported
Content-Type 不被支持 HttpMediaTypeNotSupportedException 415 AGENT_BAD_REQUEST —
真实内部故障 其他 Exception 500 AGENT_INTERNAL_ERROR —（只记日志，不回传内部消息）

为什么这条约定重要：前端在 VITE_DATA_SOURCE=api 下要按状态码分流—— 404 说明该端点尚未实现（契约里 x-wp-status: planned），应走「演示数据 + 降级标注」路径； 5xx 说明服务故障，应走「降级横幅」路径。二者混在一起前端只能猜。 实测曾因此在未部署新端点的进程上把 GET /api/body/knowledge/reconcile 的 404 误判为服务故障。

5.2 工具域专属错误码（tool-executor，2026-09-19 新增）¶

tool-executor（8084）的 ErrorCode 在上述 11 个通用码之上额外定义 6 个工具域码 （与 contracts/work-platform-bff-openapi.yaml 的 ErrorEnvelope.code.enum 同源副本）：

错误码 HTTP 默认消息 触发场景
AGENT_TOOL_NOT_ALLOWED 403 工具不在白名单或被禁用 ToolGuard 白名单闸拒绝 / 工具已 deprecated
AGENT_TOOL_ARGS_INVALID 400 工具参数校验失败 Draft-07 JSON Schema 校验不通过
AGENT_TOOL_ARGS_BLOCKED 403 参数命中安全拦截规则 staticCodeScan 命中 12 条敏感规则（rm -rf、提权、出网等）
AGENT_SANDBOX_REJECTED 403 沙箱拒绝执行 SandboxExecutor 判定载荷不可执行
AGENT_TOOL_CIRCUIT_OPEN 503 工具熔断中，暂不可用 连续失败 3 次 → 熔断窗口 30s
AGENT_TOOL_EXEC_FAILED 500 工具执行失败 沙箱内进程非零退出 / 超时

工具调用失败时仍返回统一错误信封，details 携带 call_id / audit_id 便于回查审计。 完整异常语义另见 docs/异常流程归纳.md。

回归守卫：三个模块各有一个 common/GlobalExceptionHandlerTest（session 5 / sense 5 / body 6 项）， 其中 genuineServerFaultStillMapsTo500 是必需的边界用例——防止为了修 404 而把兜底分支整体改掉。 新增 HTTP 服务模块时请照抄这套用例。

非 Java 侧的同一套语义（2026-09-18 对齐；此前二者分别用了 {error} 与 FastAPI 默认 {detail}）：

服务 实现落点 404 / 405
wp-bff server.js 的 fail() + ROUTE_GUARD 路径不存在 → 404；路径命中但方法不符 → 405 + Allow 头（ROUTE_GUARD 由 IMPLEMENTED_ENDPOINTS 派生，不另立端点真相）
nlp-service app/main.py 的三个 @app.exception_handler 同左（透传框架 Allow 头）；422 归并为 400

完整端到端异常传播链（含降级链路、planned 三态判定与排障决策树）见 docs/异常流程归纳.md。

注意：gateway-service 不实现 GlobalExceptionHandler —— 它在 JwtAuthFilter.reject() 里手写同样格式的 JSON，以保持客户端只需一套解析逻辑。 新增网关侧错误响应时请沿用 {"code","message","details":{}} 格式。

body-service 已接入该体系（Phase 3）：新增 common 包三件套 （ErrorCode / BizException / GlobalExceptionHandler），响应格式与其余服务一致。

5.2 重复定义的维护成本¶

ErrorCode 现在是三份物理副本（session-manager / sense-service / body-service）， 无编译期约束保证同步。新增/修改错误码必须三处同改，否则同一语义在不同服务返回不同 code。 下沉到 common-java 模块或 proto-contracts 是已登记的改进项（见 §10 缺口 4）。

6. 消息通道与主题命名¶

两条通道职责不同，不要混用：

通道 实现 用途 可靠性
NATS session 用 jnats；sense 用自研 MinimalNatsClient 同步请求-应答（RPC） 尽力而为，失败即降级
Kafka Kafka clients 领域事件（持久化） acks=all，是权威事件通道

已使用的主题/学科：

通道 名称 生产者 消费者 语义
NATS lifeform.rpc.sense.ping session sense 总线健康探测（返回 pong）
NATS lifeform.rpc.sense.collect （预留） sense R1 动态采集指令
Kafka lifeform.session.created session session（审计打印） 会话创建事件
Kafka lifeform.sense.collected sense body-service（SenseCollectedConsumer） 采集完成（仅 ACCEPTED）→ 知识入库

命名约定：Kafka 为 lifeform.{domain}.{event}，NATS RPC 为 lifeform.rpc.{target}.{action}。

两个实现细节：

  • NATS 主题用具体名而非通配。NatsBusServer 的注释指出：Docker NATS 环境下通配订阅投递失效， 因此显式订阅两个具体主题，新增 RPC 必须显式登记。相反，session-manager 用的是 jnats，不受此限制。
  • lifeform.sense.collected 的负载：Phase 2 时只有元数据与 staging_ref； Phase 3 起扩展为携带 title / content（使事件自洽，躯体层无需回读暂存即可入库）。 超长正文的暂存回读路径登记为后续优化（见 §10 缺口 11）。

7. gRPC 健康探针¶

四个 Java 服务各有一个逻辑完全相同的 grpc/GrpcHealthServer（仅端口不同）：

  • 实现 SmartLifecycle，容器启停时管理 Server；
  • 读 ${grpc.port:0}，端口 ≤ 0 时跳过启动（便于本地关闭）；
  • 用 HealthStatusManager 把空服务名 ""（代表整个服务器）注册为 SERVING；
  • 启动失败抛 IllegalStateException（让容器启动失败，不静默降级）；
  • 不依赖 Spring Boot 的 gRPC 自动配置（官方无此能力，手写 30 行更轻）。

为什么四个模块各写一份而不抽公共类：为避免在 proto-contracts 里引入 Spring 依赖 —— 该模块是被所有服务依赖的编译期基础，保持"零 Spring 依赖"比复用 30 行代码更重要。

9. HTTP 客户端约定（缺陷 D-1）¶

这是本项目最容易重复踩的坑，两个模块都做了统一收口：

模块 收口类 用法
session-manager orchestration/OutboundHttp OutboundHttp.restClient(baseUrl)
sense-service util/HttpClients HttpClients.builder(timeout)

绝对不要直接写 RestClient.builder().build() 或 HttpClient.newHttpClient()。

根因回顾：JDK HttpClient 默认协商 HTTP/2，对明文连接会先发 Upgrade: h2c + HTTP2-Settings； uvicorn(h11) 不兼容该升级，会丢弃请求体，于是 FastAPI 报 422「body Field required」， Java 侧只看到"上游不可用"。

这个缺陷的隐蔽性极高：TCP 可连、健康检查通过、HTTP 状态码正常 —— 只有请求体丢了。因此两侧都有专门的回归守卫测试（OutboundHttpTest、HttpClientsTest）， 用裸 ServerSocket 抓原始报文断言请求行是 HTTP/1.1 且无升级头。

新增跨服务调用时：一律经上述收口类构建客户端，并确认目标服务是 HTTP/1.1 兼容的。

9.1 跨服务超时预算（2026-09-19 新增）¶

设超时值时，必须同时写下「对端该操作的最坏耗时」 —— 两个数字分开看各自都合理， 放在一起才可能错。这一节是那类缺陷的权威口径。

权威登记表：contracts/timeout-budget.yaml（19 条边，逐条记录调用方/被调方/操作/ 上游预算/下游最坏耗时/耗时依据/代码锚点/状态）。门禁：

python scripts/timeout-budget-check.py            # 语义 + 锚点 + 魔法数字三层校验
python scripts/timeout-budget-check.py --strict   # 修复期：已登记的 gap 也算失败
python scripts/timeout-budget-check.py --list     # 打印全表摘要（预算/余量/状态）

不变量：上游预算 ≥ 下游最坏耗时 × 1.5（余量比 1.5 而非 1.2 —— 实测 1.4x 仍出过事）。 两类边豁免余量校验但需显式声明 exempt_headroom: true：docker 启停 watchdog、 TCP 健康探针（其超时是预期结果而非失败）。

wp-bff 侧档位（按「操作类型」分档，不按端点硬编码；均可用 WP_BFF_*_TIMEOUT_MS 覆盖）：

档位 默认 适用 下游最坏依据
READ 5000 纯查询（Redis / 进程内 / PG 索引） 毫秒~1s
RETRIEVE 15000 检索型 body-service 读超时 10s
GENERATE 45000 LLM 生成型 LLM 级联最坏 22s（L2 8s×2 + L1 3s×2）
WRITE 60000 写入型（入库含嵌入） 嵌入读超时 30s
EXECUTE 60000 工具执行 沙箱超时 10s / HTTP 工具读超时 15s
SANDBOX_PROBE 9000 容器探测 docker CLI 冷探测 5.7s
MIDDLEWARE_START / _STOP 180000 / 120000 容器启停 watchdog 启动实测 10~30s（豁免余量）

三条纪律：

  1. 生成型链路必须显式声明 GENERATE 档，不得依赖默认值 —— 落到 READ 默认会「把 LLM 稍慢误报为大脑层不可用」。
  2. 读型端点必须保持短预算 —— 为修「慢」把读型也拉到 45s， 会让真实故障等 45s 才暴露降级。两条不变量都有 wp-bff 用例守着。
  3. 调用点不得就地写数字（如 timeoutMs: 30000）—— 锚点校验锚的是常量定义， 看不见调用点的字面值；故门禁另有一层魔法数字扫描。

session-manager 侧档位（2026-09-19 新增，同一理念：按用途具名，不共用默认读超时）：

档位 默认 适用 下游最坏依据
INTENT_TIMEOUT 5000 nlp 意图识别（规则级联，毫秒级） 毫秒级
RETRIEVE_TIMEOUT 15000 body 检索（问答上下文） body 端到端预算 10s（余量 1.5x）
BRAIN_TIMEOUT 30000 nlp /brain/ask 生成 nlp 总预算 20s（余量 1.5x，GAP-01 已闭合）
DEFAULT_READ_TIMEOUT 10000 兜底（未声明用途的读） ——

nlp-service 侧预算（app/budget.py，统一由 run_with_budget() 包裹）：

预算 默认 适用 超时行为
BRAIN_TOTAL_BUDGET_MS 20000 /brain/ask 的检索 + 生成共享预算（GAP-01 闭合：25s→20s，级联在预算内被截断） 504 AGENT_TIMEOUT
EMBED_BUDGET_MS 12000 /api/nlp/embed 同上

body-service 侧预算（2026-09-19 GAP-05 闭合新增）：

预算 默认 适用 超时行为
RETRIEVAL_TOTAL_BUDGET_MS 10000 /retrieve warm 管线（嵌入 + Qdrant + 重排共享，BudgetGuard 执行） 504 AGENT_TIMEOUT（绝不返回空结果冒充"无结果"）

为什么必须给下游自己一个上限：Python 侧原先的"超时"完全由调用方决定，自己没有上限， 于是「下游最坏耗时」不可证明，上游余量比根本算不出来（旧 GAP-03 / GAP-04 即此）。 加上预算后，下游最坏从"不可证明"变成"有界"，两条缺口随之闭合。

本轮闭合的 gap（2026-09-19，GAP 收尾轮 —— 方向统一为内层收敛、外层覆盖）：

已闭合 边 闭合方式
GAP-01 session-manager → nlp /brain/ask 收紧下游：BRAIN_TOTAL_BUDGET_MS 25s→20s（原 25s > 级联最坏 22s、从不构成约束）；30s / 20s = 1.5x。不选"上游抬到 33s"——那会把 session 总预算顶到 38s，反把 GAP-06 恶化到需 ≥57s
GAP-05 nlp → body 检索 下游加端到端预算：body RETRIEVAL_TOTAL_BUDGET_MS = 10s（原表把"出站读超时 10s"误当端到端最坏，真实管线 = 嵌入 12s + Qdrant 2s + 重排 10s）；上游 RETRIEVAL_BUDGET_MS 8s→15s 并回收第二套口径。15s / 10s = 1.5x
GAP-06 wp-bff → session /ask 单列档位：新增 ASK 档 53s（35s × 1.5 = 52.5s）只服务本边；GENERATE 档保持 45s（被 /brain/ask 等多条边共享，不宜随本边抬高）

GAP-06 是新出现的，不是回归：REC-01 让 session 一次 ask 的最坏耗时变得可信 （从"单个读超时 10s"变成"总预算 35s"），代价是 wp-bff 侧 45s 的余量比被摊薄到 1.29x。 记录它的意义在于：给下游加预算上限会同时改变上游余量比，两侧必须同轮复核 —— 否则"闭合一个缺口"会悄悄制造另一个。

根本方向（REC-01，本轮已落地主体）：LLM 级联原缺总预算上限，最坏耗时是 「各级超时 × 重试次数」的乘积，随层级与重试数膨胀。现已实现 deadline propagation：

  • llm_gateway.generate(request, deadline_ms=...) —— 级联每一级的有效超时取 min(该级超时, 剩余总预算)，并统计 deadline_exceeded；
  • pipeline.run(..., deadline_ms=...) —— 检索与生成共享同一个 deadline，不再各自为政；
  • session-manager RequestBudget —— 每一跳读超时取 min(该跳档位, 剩余预算)， 预算耗尽时不发起调用，如实降级并标注 budget_exhausted。

GAP-01 / GAP-05 已于同日 GAP 收尾轮闭合：nlp 上限真正收紧到 20s（级联在预算内被截断）； body 检索链路补上端到端 deadline（BudgetGuard，REC-01 同路线）。跨服务预算余量全部 ≥ 1.5x。

启动前自检：./scripts/start.sh gate（all 模式会自动带跑）。 门禁失败不静默忽略也不硬拦，需显式 SKIP_BUDGET_GATE=1 跳过，跳过时打印免责提示。

11. 本地启动顺序¶

# ① 基础设施（仓库根）
cp .env.example .env          # 首次
docker compose up -d          # 8 个中间件：postgres/redis/nats/kafka/qdrant/minio/nacos/jaeger

# ② 校验引擎与容器
docker version --format '{{.Server.Version}}'
docker ps --format '{{.Names}}\t{{.Status}}'

# ③ Python 意图服务（可选，缺失时 session 会降级为 FALLBACK）
cd services/python/nlp-service
../venv/Scripts/python.exe -m uvicorn app.main:app --port 8000

# ④ Java 服务（四个终端，或用 IDE 启动）
cd services/java
../../scripts/mvn-dev.sh clean package
JWT_SECRET=<至少32字节的密钥> ../../scripts/mvn-dev.sh -pl gateway-service spring-boot:run
../../scripts/mvn-dev.sh -pl session-manager spring-boot:run
../../scripts/mvn-dev.sh -pl sense-service spring-boot:run
../../scripts/mvn-dev.sh -pl body-service spring-boot:run

# ⑤ 中间件观测（前端 /middleware 依赖它）
cd services/node/wp-bff && node server.js      # 127.0.0.1:8090

# ⑥ 前端
cd web/work-platform && npm run dev            # 默认 3001

依赖顺序说明：

  • gateway-service 必须在 JWT_SECRET 有值时可启动 —— 不设则启动失败（这是刻意的安全设计）。
  • 业务服务可以先于其上游启动：session-manager 在 nlp-service / body-service 未就绪时会降级（默认开关开启），不会启动失败。
  • sense-service 在 MinIO / NATS / Kafka 任一不可用时都能启动（各自独立降级）， 但功能会相应受限：
  • MinIO 不可用 → 暂存降级到本地文件；
  • OCR 不可用 → 视觉渠道 DEGRADED；
  • 未配情报源 → 嗅觉渠道 DOWN；
  • NATS 不可用 → 总线指令通道失效（HTTP 采集路径仍可用）。
  • body-service 只依赖 Nacos，最简单。

健康检查命令：
