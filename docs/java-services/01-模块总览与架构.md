# 01 · 模块总览与架构

> 本文说明 `services/java` 下五个 Maven 模块的职责边界、协作方式与运行形态。
> 读完这篇应能回答：「我要改的功能应该在哪个模块？」

## 1. 生命体分层与模块映射

项目用「人体生命体」隐喻组织架构，各层落到 Java 侧的映射关系如下：

| 生命体层 | 对应能力 | 当前落地模块 | 状态 |
|---|---|---|---|
| 大脑层 | 意图识别、会话状态、任务规划 | `session-manager`（编排）+ `nlp-service`（Python，意图） | Phase 1/2 部分 |
| 感官层 | 文本 / URL / 文件 / 图像采集 | `sense-service` | **Phase 2 已实现** |
| 躯体层 | 知识库、向量检索、RAG | `body-service`（三层存储 + 语义检索 + RAG） | **Phase 3 已实现** |
| 四肢层 | 工具调用、代码执行、沙箱 | `tool-executor`（注册表 + 执行引擎 + 沙箱 + 审计） | **Phase 5 已实现** |
| 小脑层 | DAG、Saga、多 Agent 编排 | — | Phase 6+ |
| 免疫层 | 安全、容错、审批、多租户 | 横切：网关 JWT + 租户注入 + `OutboundGuard` | 持续增强 |
| 进化层 | 反馈学习、知识自愈 | — | Phase 8 |

其中 `gateway-service` 不属于任何「器官」，它是**统一的脊柱入口**：所有外部流量从这里进，
在这里完成鉴权、租户注入与路由分发。

## 3. 模块依赖关系

```text
                        ┌──────────────────────┐
   外部请求 ──────────▶  │   gateway-service    │  8080
                        │  路由 / JWT / 租户    │
                        └──────────┬───────────┘
                                   │ lb:// 服务发现（Nacos）
          ┌──────────────┬─────────┴────────┬──────────────┬──────────────┐
          ▼              ▼                  ▼              ▼              ▼
   /api/session/**  /api/sense/**     /api/nlp/**    /api/body/**   /api/tool/**
          │              │                  │              │              │
   ┌──────▼──────┐  ┌────▼─────┐     ┌──────▼─────┐  ┌─────▼──────┐ ┌─────▼──────┐
   │  session-   │  │  sense-  │     │  nlp-      │  │   body-    │ │   tool-    │
   │  manager    │  │  service │     │  service   │  │  service   │ │  executor  │
   │    8081     │  │   8082   │     │  (Python)  │  │    8083    │ │    8084    │
   └──┬───┬───┬──┘  └────┬─────┘     └────────────┘  └─────▲──────┘ └─────▲──────┘
      │   │   │          │                                  │              │
      │   │   └──HTTP────┼──────────────────────────────────┘              │
      │   │              │  返回检索结果                                   │
      │   └──HTTP────────┼──▶ nlp-service /api/nlp/intent                  │
      │                  │                                                 │
      └──NATS / Kafka────┴──▶ 消息总线（脊柱神经）                          │
                                                                           │
   （Phase 5+）大脑规划器 / 组合任务 ──HTTP /api/tool/execute──────────────┘

  所有模块 ──▶ proto-contracts（编译期依赖，含 gRPC 契约与 Health 服务）
```

要点：

- **`proto-contracts` 是被所有模块依赖的编译期基础**，不独立部署。
- **`session-manager` 同时使用两种通信风格**：对 `nlp-service` / `body-service` 走同步 HTTP（问答需要即时结果）；
  对 `sense-service` 走 NATS 请求-应答（异步采集，允许延迟）。
- **`sense-service` 不反向调用 `session-manager`**，采集结果通过事件（`lifeform.sense.collected`）广播，
  由 Phase 3 的入库消费者订阅 —— 保证感官层与大脑层解耦。
- **`tool-executor` 是平台唯一允许执行外部动作的模块**（算数 / 出网 / 跑代码）；
  它对上游只提供一条无状态 HTTP 契约，不反向调用任何服务，审计真相源是自己的 PG 表
  `tool_audit_log`（Kafka 仅事件旁路）。

## 4. 两条主要链路

### 4.1 VS1 问答链路（Phase 1 打通，当前主干）

```text
POST /api/session                     → 创建会话（Redis 存状态）
POST /api/session/{id}/ask            → 提问
  ├─ NlpClient  → nlp-service         → 意图识别（规则优先 → L0 模型兜底）
  ├─ BodyClient → body-service        → 检索知识片段
  └─ 模板拼装 answer（不依赖 LLM）    → 返回 + 落消息历史
```

降级行为：`nlp-service` 或 `body-service` 不可用时，默认按配置降级
（意图 → `FALLBACK` 闲聊、检索 → 空结果），仍能返回模板回答，而不是整条链路 503；
显式关闭降级时返回 502 语义的 `AGENT_UPSTREAM_UNAVAILABLE` 并保留根因。

### 4.2 感官采集链路（Phase 2 新增）

```text
两种触发方式：
  R0 定时调度（R0Scheduler，规则驱动）  ─┐
  R1 动态指令（HTTP /api/sense/command）─┤
  R1 总线指令（NATS，R1-04 脊柱信号）   ─┘
                                        ▼
                            CollectPipeline（路由 + 退避重试 + 降级）
                                        ▼
                     SenseChannel 五感渠道（触/视/嗅/味/听）
                                        ▼
                            DataNormalizer（五字段打标）
                                        ▼
                     QualityGate（硬规则 + 评分，低质直接拦截）
                                        ▼
                     StagingStore（MinIO / 本地，隔离暂存 + 批次回滚）
                                        ▼
                     SenseEventPublisher（lifeform.sense.collected）
```

治理设施环绕这条链路：`ChannelHealthMonitor`（探针 / 隔离 / 恢复）、
`DeadLetterStore`（重试耗尽登记）、`SenseMetrics`（供 Console 感官视图）。

## 7. 构建与运行

### 7.1 构建（本机特有关键约束）

**不要直接使用 `mvn`** —— 本机 `mvn.cmd` 已损坏。所有构建走仓库根的包装脚本：

```bash
cd services/java

# 全量构建 + 测试
../../scripts/mvn-dev.sh clean package

# 只跑单个模块（根 POM 在 services/java 下，必须在此目录执行 -pl）
../../scripts/mvn-dev.sh -pl sense-service -am test
```

`scripts/mvn-dev.sh` 通过 `plexus-classworlds` 启动器直调 Maven，绕开损坏的 `mvn.cmd`。

另外两点容易踩：

- **`rm -rf target` 会被安全策略拦截**，清理请用 Maven 自带 `clean` 目标。
- **默认生命周期不会调用 `protoc`** —— 生成的 proto 源码已入库，原因见 [02-proto-contracts](02-proto-contracts.md)。

### 7.2 启动依赖

各服务启动前需以下基础设施就绪（由仓库根 `docker-compose.yml` 提供）：

| 服务 | 依赖 |
|---|---|
| `gateway-service` | Nacos（服务发现） |
| `session-manager` | Nacos、Redis（会话存储） |
| `sense-service` | Nacos、MinIO（暂存，缺失时自动降级本地）、NATS（R1 总线指令） |
| `body-service` | Nacos |

MinIO 缺失不会导致 `sense-service` 启动失败 —— `StagingStore` 会自动降级到本地文件后端，
保证「低质拦截 + 批次可回滚」始终成立。
