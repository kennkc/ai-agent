# 07 · 运行时配置与横切约定

> 本文汇总四个 Java 服务的**配置、端口、环境变量**，以及跨模块的**横切约定**
> （多租户、错误码、观测、消息主题、HTTP 客户端）。部署、联调、排障时看这一篇。

## 1. 端口与实例对照

| 服务 | HTTP | gRPC | Nacos 服务名 | 声明位置 |
|---|---:|---:|---|---|
| `gateway-service` | 8080 | 9091 | `gateway-service` | 各自 `application.yml` |
| `session-manager` | 8081 | 9092 | `session-manager` | 同上 |
| `sense-service` | 8082 | 9093 | `sense-service` | 同上 |
| `body-service` | 8083 | 9094 | `body-service` | 同上 |

**HTTP 端口是写死的字面值**（如 `server.port: 8082`），没有做环境变量占位 ——
多实例部署时需要另行处理。

## 4. 多租户契约（最关键的横切约定）

**数据流**：JWT 声明里的 `tenant_id` → 网关注入请求头 `X-Tenant-Id` → 各业务服务从请求头读取。

| 环节 | 责任 | 实现位置 |
|---|---|---|
| 令牌签发 | 把 `tenant_id` 写入 JWT 自定义声明 | `gateway/security/JwtService.sign` |
| 身份校验 + 注入 | 解析令牌，**覆写** `X-Tenant-Id` 请求头 | `gateway/security/JwtAuthFilter` |
| 业务读取 | 只信任请求头，忽略请求体内同名字段 | 各 Controller 的 `@RequestHeader("X-Tenant-Id")` |
| 数据隔离 | 会话/暂存/知识均按租户分区 | `SessionController.requireOwnedSession`、`BodyStore.tenantChunks`、`StagingStore` |

**三条不可违反的规则**：

1. **业务服务不得信任请求参数里的租户 ID**。`sense-service` 的 `SenseController.collect`
   从请求体收到 `tenant_id` 也会**忽略**，只用请求头的值（见
   [05-sense-service](05-sense-service.md) §5.5）。
2. **按 ID 访问租户资源必须校验归属**。`SessionController` 的 `requireOwnedSession`
   返回 403 而非 404（明确告知无权访问）。新增接口必须复用该模式。
3. **`defaultValue = "default"` 是个隐患**。所有 `@RequestHeader("X-Tenant-Id")` 都带默认值，
   因此**绕过网关直连服务时，请求会自动落入 `default` 租户而不报错**。
   开发期方便，生产环境应确保业务服务端口不对外暴露，或考虑移除默认值。

## 5. 统一响应与错误码

**成功响应**：各接口自定义结构（无统一包装层）。

**错误响应**（三个服务一致）：

```json
{ "code": "AGENT_NOT_FOUND", "message": "session not found: xxx", "details": {} }
```

**错误码表**（`session-manager` / `sense-service` / `body-service` **各有一份内容完全相同**的
`ErrorCode` 枚举，共 11 个值）：

| 错误码 | HTTP | 默认消息 |
|---|---:|---|
| `AGENT_BAD_REQUEST` | 400 | 请求参数不合法 |
| `AGENT_UNAUTHORIZED` | 401 | 未认证或 Token 无效 |
| `AGENT_FORBIDDEN` | 403 | 无权限访问 |
| `AGENT_NOT_FOUND` | 404 | 资源不存在 |
| `AGENT_METHOD_NOT_ALLOWED` | 405 | 请求方法不被支持 |
| `AGENT_CONFLICT` | 409 | 资源冲突 |
| `AGENT_DUPLICATE` | 409 | 资源已存在 |
| `AGENT_TIMEOUT` | 504 | 调用超时 |
| `AGENT_BUS_UNAVAILABLE` | 503 | 总线通道不可用 |
| `AGENT_UPSTREAM_UNAVAILABLE` | 502 | 上游服务不可用 |
| `AGENT_INTERNAL_ERROR` | 500 | 服务内部错误 |

### 5.1 路由层异常分流（2026-09-18 新增，**三服务同源**）

`GlobalExceptionHandler` 除了业务异常，还**必须**为路由层三类异常单独映射——
它们不经过任何控制器，若落进兜底 `@ExceptionHandler(Exception.class)` 会返回 500，
使「调用姿势不对」与「服务真的坏了」在客户端**不可区分**：

| 触发场景 | Spring 异常 | 返回 | details |
|---|---|---|---|
| 路径不存在（无控制器匹配） | `NoResourceFoundException`（Boot 3.2+）/ `NoHandlerFoundException` | **404** `AGENT_NOT_FOUND` | `path` |
| 路径存在但方法不对 | `HttpRequestMethodNotSupportedException` | **405** `AGENT_METHOD_NOT_ALLOWED` | `method` / `supported` |
| `Content-Type` 不被支持 | `HttpMediaTypeNotSupportedException` | **415** `AGENT_BAD_REQUEST` | — |
| 真实内部故障 | 其他 `Exception` | **500** `AGENT_INTERNAL_ERROR` | —（只记日志，不回传内部消息） |

**为什么这条约定重要**：前端在 `VITE_DATA_SOURCE=api` 下要按状态码分流——
`404` 说明**该端点尚未实现**（契约里 `x-wp-status: planned`），应走「演示数据 + 降级标注」路径；
`5xx` 说明**服务故障**，应走「降级横幅」路径。二者混在一起前端只能猜。
实测曾因此在未部署新端点的进程上把 `GET /api/body/knowledge/reconcile` 的 404 误判为服务故障。

**回归守卫**：三个模块各有一个 `common/GlobalExceptionHandlerTest`（session 5 / sense 5 / body 6 项），
其中 `genuineServerFaultStillMapsTo500` 是**必需的边界用例**——防止为了修 404 而把兜底分支整体改掉。
新增 HTTP 服务模块时请照抄这套用例。

**注意**：`gateway-service` **不实现** `GlobalExceptionHandler` ——
它在 `JwtAuthFilter.reject()` 里手写同样格式的 JSON，以保持客户端只需一套解析逻辑。
新增网关侧错误响应时请沿用 `{"code","message","details":{}}` 格式。

**`body-service` 已接入该体系**（Phase 3）：新增 `common` 包三件套
（`ErrorCode` / `BizException` / `GlobalExceptionHandler`），响应格式与其余服务一致。

### 5.2 重复定义的维护成本

`ErrorCode` 现在是**三份物理副本**（`session-manager` / `sense-service` / `body-service`），
无编译期约束保证同步。**新增/修改错误码必须三处同改**，否则同一语义在不同服务返回不同 code。
下沉到 `common-java` 模块或 `proto-contracts` 是已登记的改进项（见 §10 缺口 4）。

## 6. 消息通道与主题命名

两条通道职责不同，**不要混用**：

| 通道 | 实现 | 用途 | 可靠性 |
|---|---|---|---|
| **NATS** | session 用 jnats；sense 用自研 `MinimalNatsClient` | 同步请求-应答（RPC） | **尽力而为**，失败即降级 |
| **Kafka** | Kafka clients | 领域事件（持久化） | `acks=all`，是**权威事件通道** |

**已使用的主题/学科**：

| 通道 | 名称 | 生产者 | 消费者 | 语义 |
|---|---|---|---|---|
| NATS | `lifeform.rpc.sense.ping` | session | sense | 总线健康探测（返回 `pong`） |
| NATS | `lifeform.rpc.sense.collect` | （预留） | sense | R1 动态采集指令 |
| Kafka | `lifeform.session.created` | session | session（审计打印） | 会话创建事件 |
| Kafka | `lifeform.sense.collected` | sense | **body-service（`SenseCollectedConsumer`）** | 采集完成（仅 ACCEPTED）→ 知识入库 |

**命名约定**：Kafka 为 `lifeform.{domain}.{event}`，NATS RPC 为 `lifeform.rpc.{target}.{action}`。

**两个实现细节**：

- **NATS 主题用具体名而非通配**。`NatsBusServer` 的注释指出：Docker NATS 环境下通配订阅投递失效，
  因此显式订阅两个具体主题，新增 RPC 必须显式登记。相反，`session-manager` 用的是 jnats，不受此限制。
- **`lifeform.sense.collected` 的负载**：Phase 2 时只有元数据与 `staging_ref`；
  **Phase 3 起扩展为携带 `title` / `content`**（使事件自洽，躯体层无需回读暂存即可入库）。
  超长正文的暂存回读路径登记为后续优化（见 §10 缺口 11）。

## 7. gRPC 健康探针

四个 Java 服务各有一个**逻辑完全相同**的 `grpc/GrpcHealthServer`（仅端口不同）：

- 实现 `SmartLifecycle`，容器启停时管理 `Server`；
- 读 `${grpc.port:0}`，**端口 ≤ 0 时跳过启动**（便于本地关闭）；
- 用 `HealthStatusManager` 把空服务名 `""`（代表整个服务器）注册为 `SERVING`；
- 启动失败抛 `IllegalStateException`（让容器启动失败，不静默降级）；
- 不依赖 Spring Boot 的 gRPC 自动配置（官方无此能力，手写 30 行更轻）。

**为什么四个模块各写一份而不抽公共类**：为避免在 `proto-contracts` 里引入 Spring 依赖 ——
该模块是被所有服务依赖的编译期基础，保持"零 Spring 依赖"比复用 30 行代码更重要。

## 9. HTTP 客户端约定（缺陷 D-1）

**这是本项目最容易重复踩的坑，两个模块都做了统一收口**：

| 模块 | 收口类 | 用法 |
|---|---|---|
| `session-manager` | `orchestration/OutboundHttp` | `OutboundHttp.restClient(baseUrl)` |
| `sense-service` | `util/HttpClients` | `HttpClients.builder(timeout)` |

**绝对不要直接写 `RestClient.builder().build()` 或 `HttpClient.newHttpClient()`**。

根因回顾：JDK `HttpClient` 默认协商 HTTP/2，对明文连接会先发 `Upgrade: h2c` + `HTTP2-Settings`；
**uvicorn(h11) 不兼容该升级，会丢弃请求体**，于是 FastAPI 报 422「body Field required」，
Java 侧只看到"上游不可用"。

**这个缺陷的隐蔽性极高**：TCP 可连、健康检查通过、HTTP 状态码正常 ——
只有请求体丢了。因此两侧都有专门的回归守卫测试（`OutboundHttpTest`、`HttpClientsTest`），
用裸 `ServerSocket` 抓原始报文断言请求行是 `HTTP/1.1` 且无升级头。

**新增跨服务调用时**：一律经上述收口类构建客户端，并确认目标服务是 HTTP/1.1 兼容的。

## 11. 本地启动顺序

```bash
# ① 基础设施（仓库根）
cp .env.example .env          # 首次
docker compose up -d          # 8 个中间件：postgres/redis/nats/kafka/qdrant/minio/nacos/jaeger

# ② 校验引擎与容器
docker version --format '{{.Server.Version}}'
docker ps --format '{{.Names}}\t{{.Status}}'

# ③ Python 意图服务（可选，缺失时 session 会降级为 FALLBACK）
cd services/python/nlp-service
../venv/Scripts/python.exe -m uvicorn app.main:app --port 8000

# ④ Java 服务（四个终端，或用 IDE 启动）
cd services/java
../../scripts/mvn-dev.sh clean package
JWT_SECRET=<至少32字节的密钥> ../../scripts/mvn-dev.sh -pl gateway-service spring-boot:run
../../scripts/mvn-dev.sh -pl session-manager spring-boot:run
../../scripts/mvn-dev.sh -pl sense-service spring-boot:run
../../scripts/mvn-dev.sh -pl body-service spring-boot:run

# ⑤ 中间件观测（前端 /middleware 依赖它）
cd services/node/wp-bff && node server.js      # 127.0.0.1:8090

# ⑥ 前端
cd web/work-platform && npm run dev            # 默认 3001
```

**依赖顺序说明**：

- `gateway-service` 必须在 `JWT_SECRET` 有值时可启动 —— **不设则启动失败**（这是刻意的安全设计）。
- 业务服务可以**先于**其上游启动：`session-manager` 在 `nlp-service` / `body-service`
  未就绪时会降级（默认开关开启），不会启动失败。
- `sense-service` 在 MinIO / NATS / Kafka 任一不可用时都能启动（各自独立降级），
  但功能会相应受限：
  - MinIO 不可用 → 暂存降级到本地文件；
  - OCR 不可用 → 视觉渠道 DEGRADED；
  - 未配情报源 → 嗅觉渠道 DOWN；
  - NATS 不可用 → 总线指令通道失效（HTTP 采集路径仍可用）。
- `body-service` 只依赖 Nacos，最简单。

**健康检查命令**：

```bash
curl -s http://127.0.0.1:8080/actuator/health | python -m json.tool     # 网关（免鉴权）
curl -s http://127.0.0.1:8082/api/sense/health                          # ⚠ 需经网关+令牌，或直连 8082
curl -s http://127.0.0.1:8083/api/body/health                           # body 自带健康端点
```

注意 `/actuator/**` 与 `/api/auth/**` 是网关的免鉴权前缀，其余路径都需要 Bearer 令牌。
