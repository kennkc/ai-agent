8.4 缺陷 D-1：JDK HttpClient 的 h2c 升级打挂 Python 服务调用（已于 2026-09-13 修复）¶

现象：同一 URL，curl 直连 nlp-service 返回 200，但 session-manager 调用恒 503；nlp-service 侧日志为：

POST /api/nlp/intent HTTP/1.1" 422 Unprocessable Entity
WARNING:  Unsupported upgrade request.
WARNING:  Invalid HTTP request received.

定位（最小复现，无需改任何源码）：用 JDK 21 单文件程序对同一 URL、同一 JSON 分别以 HTTP/2 与 HTTP/1.1 发送：

HTTP_2   -> HTTP 422  {"detail":[{"type":"missing","loc":["body"],"msg":"Field required","input":null}]}
HTTP_1_1 -> HTTP 200  {"intent":"闲聊","confidence":0.5,"engine":"FALLBACK",...}

根因：session-manager 的 NlpClient / BodyClient 使用 RestClient.builder().baseUrl(...).build()，底层默认是 JdkClientHttpRequestFactory → java.net.http.HttpClient，其默认 version = HTTP_2。对明文连接，JDK 客户端会先发 Connection: Upgrade, HTTP2-Settings / Upgrade: h2c 做协议升级握手；uvicorn(h11) 不支持 h2c，直接把请求体吞掉 → FastAPI 报 422 Field required(body) → Java 侧抛 RestClientException → 包装成 503。

影响面：NlpClient（意图识别）与 BodyClient（知识检索）同一写法，即 VS1 问答链路的两步外部调用在真实运行时都不可用。此前的健康检查只探端口/actuator，不触发跨服务调用，因此该缺陷被全绿的 healthcheck 掩盖。

建议修法（2 个文件、各 2 行，强制 HTTP/1.1）：

HttpClient http = HttpClient.newBuilder().version(HttpClient.Version.HTTP_1_1).build();
this.client = RestClient.builder().baseUrl(baseUrl)
        .requestFactory(new JdkClientHttpRequestFactory(http))
        .build();

备选：改用 Apache HttpClient 5 连接工厂；或在 nlp-service 前置一个支持 h2c 的网关。修复后应重跑 §8.3 的步骤 9–10，并补一条「跨语言服务调用」的契约用例防回归。

8.6 D-1 修复记录（2026-09-13）¶

根因再校准：准确表述不是「JDK 默认 HTTP/2 必然出错」，而是 uvicorn(h11) 不兼容 h2c 升级握手。两组对照实验：

实验 对端 HTTP_2 HTTP_1_1
1 宽松 HTTP/1.1 服务端（Python 标准库） 200，body 完好 200，body 完好
2 Tomcat（body-service） 200 200

→ 实验 1 证明 JDK 发送 Upgrade: h2c 属合规行为，宽松服务端照常接收 body；只有 uvicorn 会把请求判为非法并丢弃 body。 → 实验 2 修正此前的过度推断：BodyClient 打的是 Tomcat，从未受影响；受影响的是 NlpClient 与 VisualChannel 的 OCR POST（两者都打 uvicorn）。
