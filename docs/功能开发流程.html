Agent-Lifeform 功能开发流程¶

口径时间：2026-09-17 · 代码基线：ab2ad29 本文件回答一个问题：这个项目里的每个功能，是怎么从需求走到可验收的？ 通用流水线各功能共用；逐功能一节说明各自的「需求源 → 设计 → 代码 → 契约 → 测试 → 验收」差异。

一、通用流水线（所有功能共用，8 步）¶

源自 README.md 第 8 章，§8.0 是强制前置：

步 动作 关键约束
0 同步远端并解读对方改动（git fetch → 判落后/领先 → 读 diff） 不许直接 git pull；不许在过期基线上开发；技能 git-sync-before-change
1 需求与设计对齐 先改设计文档（需求 → 开发设计 → 测试设计 → 部署），代码跟着文档走
2 契约先行 新增/修改接口，先改 proto/ 与 contracts/，再改实现
3 实现 按阶段或垂直切片改代码，不跨阶段夹带
4 测试 单测与实现同批提交；回归用例必须覆盖修过的缺陷
5 文档同步 阶段文档 + PROGRESS.md + 相关 README/索引，缺一不可
6 全量验证 Java / Python / 契约 / wp-bff / Vue，一个都不能跳
7 提交与三分支对齐 三分支 --ff-only 对齐；推送需用户明确授权

三、逐功能开发流程¶

3.1 网关与安全边界（gateway-service，8080）¶

  • 需求源：Phase1-神经期/需求设计文档.md（统一入口 + 鉴权 + 租户隔离）
  • 代码入口：GatewayApplication、路由与过滤器配置（src/main/resources/application.yml）
  • 关键约定：
  • 路由 /api/session/** /api/sense/** /api/nlp/** /api/body/** → lb://<service>
  • 业务服务不得信任请求参数里的租户 ID，一律由网关注入 X-Tenant-Id
  • 开发令牌端点 loopback-only，默认关闭，需 DEV_TOKEN_ENDPOINT_ENABLED=true
  • 测试：网关过滤链 2 项（gateway-service 测试类）
  • 验收标准：跨租户请求被拒；无 token 401；合法 token 透传租户头
  • 开发步骤：①改设计文档 ②改路由/过滤器 ③补过滤链单测（含负向：伪造租户头） ④mvn-dev.sh -pl gateway-service -am test

3.2 会话与 VS1 问答闭环（session-manager，8081）¶

  • 需求源：Phase1-神经期/需求设计文档.md（VS1：session → intent → 本地检索 → 模板回答）
  • 代码入口：SessionController（/api/session/{id}/ask）、OutboundHttp（统一 HTTP/1.1 出站客户端）
  • 关键约定：
  • 出站一律走共享 HTTP/1.1 工厂 + 连接/读超时，不要用 JDK HttpClient 默认的 HTTP/2 （h2c 升级握手会被 uvicorn/h11 拒绝，导致请求体被丢、FastAPI 回 422 → 表面 503，即 D-1 缺陷）
  • 下游不可用时优雅降级：intent → FALLBACK、检索 → 空，并回专用错误码 AGENT_UPSTREAM_UNAVAILABLE
  • 测试：10 项，含 OutboundHttpTest / UpstreamDegradeTest 两个回归守卫
  • 验收标准：POST /api/session/{id}/ask → 200；Redis session:{id}:messages LLEN=2； 停掉 nlp-service 后仍返回 200（FALLBACK）
  • 开发步骤：①改设计 ②实现 + 出站改造 ③补降级回归用例 ④起 Redis/Kafka 实测链路

3.3 感官采集链路（sense-service，8082）¶

  • 需求源：Phase2-感官期/需求设计文档.md（R2-01~R2-10 逐条验收标准与 DoD）
  • 代码入口（按 R 编号）： | 需求 | 入口 | |---|---| | R2-01 渠道抽象 | SenseChannel（Register/Collect/Healthy/Close）+ ChannelRegistry（Spring bean 自动发现） | | R2-02 触觉渠道 | TouchChannel（URL 抓取 + 本地文件 + 纯文本；jsoup 正文提取 + 编码探测） | | R2-03 保留渠道 | VisualChannel / NoseChannel / AudioChannel / TasteChannel —— 诚实上报 available() | | R2-04 归一化 | DataNormalizer（五字段打标：source_channel / tenant_id / timestamp / freshness / confidence） | | R2-05 调度 | R0Scheduler（@Scheduled 规则轮询、每规则独立间隔、日志 + 手动 runNow） | | R2-06 指令处理 | R1DynamicHandler + SenseCommand（指令 → 渠道路由 → 采集 → 响应，单轮渠道上限） | | R2-09 健康与隔离 | ChannelHealthMonitor（探活 + DEGRADED/DOWN 阈值 + 自动隔离 + 恢复跟踪）、resilience4j 指数退避 + DeadLetterStore | | R2-10 暂存 | StagingStore（MinIO/本地双后端、入库前质检闸门、批量回滚） | | R-C02 控制台 | SenseAdminController：/channels、/channels/{type}、/channels-health、/stats、/batches、/batches/{id}/rollback、/rules、/deadletters |
  • 关键约定：渠道能力不可用时必须诚实上报（available=false / DEGRADED），绝不伪造结果
  • 测试：48 项（全项目最多）
  • 验收标准：R2-01~R2-10 逐条对照 DoD；健康监控能在渠道挂掉后隔离并进入死信
  • 开发步骤：①先补需求设计文档的 R 条目与 DoD ②实现渠道/组件并注册 bean ③补单测 ④mvn-dev.sh -pl sense-service -am test ⑤补 docs/demo/Phase2-DEMO.md 的演示步骤

3.4 意图识别（nlp-service，8000）¶

  • 需求源：Phase2-感官期/需求设计文档.md（R2-07 规则引擎、R2-08 L0 + 级联）
  • 代码入口：app/intent/rules.py（关键词/正则/场景规则，覆盖 12 场景，要求 ≥10）、 app/intent/l0_model.py（轻量 L0 分类器）、app/intent/cascade.py（规则优先 → L0 兜底）、app/intent/corpus.py（留出集）
  • 验收标准（已实测）：留出集准确率 90.0%（要求 ≥85%）；P99 0.052 ms（要求 <50 ms）
  • 测试：tests/test_intent.py 15 项
  • 开发步骤：①新场景先加进 rules.py 的场景表并同步 corpus.py 留出集 ②跑 test_intent.py 看准确率是否守住 ③改语料后必须重跑准确率，别只跑通不测指标

3.5 OCR（nlp-service / app/ocr.py）¶

  • 代码入口：app/ocr.py；对外 POST /api/nlp/ocr
  • 关键约定：引擎懒初始化（导入期不初始化 PaddleOCR，否则拖慢启动）；无引擎时上报 available=false
  • 测试：tests/test_ocr.py 4 项
  • 当前状态：⚠️ 端到端未闭合 —— 需安装 PaddleOCR 或 Tesseract；在此之前视觉渠道维持 DEGRADED
  • 开发步骤：①装引擎 ②按 docs/demo/Phase2-DEMO.md 走图片采集链路 ③登记验收结论（诚实留痕）

3.7 工作平台前端（web/work-platform）¶

  • 需求源：AGENT_CONTEXT/WP-工作平台/（WP-P1 骨架 / WP-P2 五感矩阵 / WP-P4 决策沙盘 / WP-P5-P8 随阶段点亮 + 工作平台功能设计文档.md）
  • 固定更新顺序（README.md §8.3）： 1. 先改 src/config/modules.ts 与 src/types/index.ts 2. 再改路由、页面、Mock 数据、WorkPlatformDataProvider 3. 保持 Mock 与 API 数据结构一致 4. 新增页面必须同步登记：src/router/index.ts、src/layouts/PlatformLayout.vue、docs 5. npm run typecheck && npm run build，确认 dist/ 成功后再提交
  • 关键约定：
  • 路由一律动态 import()（懒加载），别退回同步 import
  • 数据源双轨：Mock / API，靠 ?ds=api 切换零 UI 改动
  • 降级必须可见：src/api/status.ts 按数据域记录降级；失败→记录，成功→清除； UI 呈现 API · 降级 N 徽标 + 横幅 + 逐模块提示。不允许静默回落 Mock
  • 中间件卡片不受全局 VITE_DATA_SOURCE 限制：始终优先真实探针，BFF 不可达才回落并标注 data_source='mock'
  • 验收标准：typecheck + build 通过；API 模式下断掉 BFF 能看见降级提示

3.8 Ops BFF 与观测区（services/node/wp-bff，8090）¶

  • 需求源：WP-工作平台 + 「观测区」需求（中间件监控 / 链路追踪）
  • 代码入口：server.js（createServer(options)，spawn/probe/fetch 可注入以便测试）、test/server.test.js
  • 关键约定：
  • 控制端点（start/stop）必须同时过来源检查（WP_BFF_ALLOWED_ORIGINS）与 控制令牌（X-WP-Control-Token，timingSafeEqual 比较）；缺失/错误 → 401，外来来源 → 403， 两种情况都写审计日志 REJECT_AUTH
  • 令牌来源：WP_BFF_CONTROL_TOKEN，否则启动时随机生成写入 logs/wp-bff-control-token（0600）并打印一次； 没有免鉴权回退模式
  • CORS：不要回 Access-Control-Allow-Origin: *，只对白名单来源回显并始终带 Vary: Origin
  • 命令形状固定 + 8 键白名单；未登记的 key → 403
  • Vite 代理在服务端读令牌文件再注入请求头 → 令牌不进浏览器包；且不重写 Origin（保持 CSRF 检查有效）
  • 测试：node --test 14 项（鉴权、CSRF、白名单、命令形状、幂等、CORS、链路回落、采样元数据）
  • 开发步骤：①改契约（x-wp-status）②改 server.js ③补回归用例 ④node --test ⑤实测 curl 一次真实端点

3.9 基础设施编排（docker-compose.yml + scripts/）¶

  • 需求源：各阶段 部署文档.md
  • 关键约定（本机特有，踩过大坑）：
  • 仓库目录已由 agent-lifeform 改名 ai-agent → compose 默认项目名随之改变， 会导致与存量容器 / 数据卷命名冲突并误建空卷 → 必须在 .env 写 COMPOSE_PROJECT_NAME=agent-lifeform 沿用存量资源
  • 根目录 .env 需提供 MINIO_ROOT_USER 等必需变量（模板见 .env.example）
  • .env 一律不入库，只有 .env.example 入库（.gitignore 用 .env + .env.* + !.env.example）
  • 验收标准：docker compose config 通过；./scripts/start.sh all && ./scripts/healthcheck.sh → 16/16 OK

3.10 契约治理（proto/ + contracts/ + scripts/contract-check.py）¶

  • 两条契约线： 1. 跨服务 gRPC/proto：proto/{session,sensor,brain,limb,body,common}/v1/（6 份） → Java 生成源码已入库（proto-contracts 90 个文件）； Python 生成物（12 个）在 services/python/nlp-service/generated/，已 gitignore、不入库； 默认生命周期不调 protoc（插件在本机清理目录时会原生阻塞、构建永久卡死）； 契约变更时 Java 用 -Pproto-gen、Python 用 scripts/proto-gen.sh 重新生成 → 逐条使用说明与变更流程见 docs/proto契约使用说明.md 2. 工作平台 BFF OpenAPI：contracts/work-platform-bff-openapi.yaml（37 端点，implemented 6 / planned 31）
  • 门禁规则（contract-check.py 三条）： 1. 实现端点必须已登记且标记 implemented 2. provider.ts 里调用的每个路径必须能匹配契约模板 3. 每个端点必须带 x-wp-status
  • 产物同步门禁（scripts/proto-sync-check.sh，2026-09-17 新增）：双向比对生成物与契约源， 报出 未入库 / 内容不同 / 契约已无 三类偏差；Python 侧另做产物数断言与 6 模块导入自检。 本地跑 bash scripts/proto-sync-check.sh all；CI 由 proto-check-python / proto-check-java 强制阻断。 （此前「改了 .proto 却忘重新生成」不会被任何检查发现，这是本轮补上的空白。）
  • 开发步骤：①改 proto/ 或 contracts/ ②改实现 ③python scripts/contract-check.py [--work-platform ...] ④若动过 proto/：重新生成两侧产物并跑 bash scripts/proto-sync-check.sh all ⑤反向验证门禁真的会拦（把 /tracing 删掉应得 FAIL 实现端点未登记契约）

3.11 文档与归档体系（docs/ + 两个脚本）¶

  • 产物与工具：
  • scripts/md2html-report.py —— Markdown → 自包含 HTML 镜像（必须 anaconda Python）
  • scripts/java-doc-coverage.py —— Java 逐文件文档覆盖率自查（有缺口退 1，可用于 CI）

  • 改 .md 必须重新生成对应 .html，两者一并提交（否则版本漂移）

  • 历史归档不回改：旧口径（如 54/73 项测试）保留原样，新口径写进当期文档并标注时间

五、本机特有坑（照做能省几小时）¶

坑 规避
mvn / mvn.cmd 会卡死（原生阻塞） 一律用 scripts/mvn-dev.sh；-pl 必须在 services/java 下执行；清目录用 Maven clean 而非 rm -rf
rm -rf target 被安全策略拦截 同上，用 clean 目标
托管 Python 没有 markdown 包 生成 HTML 用 E:/software/anaconda3/python.exe
精简 Git Bash 里 ls/head/tail 报 command not found 先 export PATH="/usr/bin:/bin:$PATH"
用 tail 截断 git 关键命令输出会吞掉错误 不要截断 fetch/checkout/merge/push 的输出
切分支后工作区文件可能从磁盘消失 切前后都 git status --porcelain 校验；多分支对齐用 push refspec
git ls-files 默认转义中文路径 → 大量假缺失 用 git ls-files -z 或直接信 git status --porcelain
github HTTPS(443) 曾长期不通 本机已改走 SSH(22)；直连间歇性波动时先重试再改配置
