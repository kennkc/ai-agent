Agent-Lifeform 功能开发流程¶

口径时间：2026-09-19 · 代码基线：Phase 5 四肢期开发线（998623a 之后再叠加四肢期代码：工具执行服务 + 工作平台执行视图） 历史口径：2026-09-18 曾以 998623a（Phase 3 主体收口 a5e0cd5 + 审核补全 / 口径对齐轮）记；Phase 4 / Phase 5 落地后按本行口径更新。 本文件回答一个问题：这个项目里的每个功能，是怎么从需求走到可验收的？ 通用流水线各功能共用；逐功能一节说明各自的「需求源 → 设计 → 代码 → 契约 → 测试 → 验收」差异。

一、通用流水线（所有功能共用，8 步）¶

源自 README.md 第 8 章，§8.0 是强制前置：

步 动作 关键约束
0 同步远端并解读对方改动（git fetch → 判落后/领先 → 读 diff） 不许直接 git pull；不许在过期基线上开发；技能 git-sync-before-change
1 需求与设计对齐 先改设计文档（需求 → 开发设计 → 测试设计 → 部署），代码跟着文档走
2 契约先行 新增/修改接口，先改 proto/ 与 contracts/，再改实现
3 实现 按阶段或垂直切片改代码，不跨阶段夹带
4 测试 单测与实现同批提交；回归用例必须覆盖修过的缺陷
5 文档同步 阶段文档 + PROGRESS.md + 相关 README/索引，缺一不可
6 全量验证 Java / Python / 契约 / wp-bff / Vue，一个都不能跳
7 提交与三分支对齐 三分支 --ff-only 对齐；推送需用户明确授权

三、逐功能开发流程¶

3.1 网关与安全边界（gateway-service，8080）¶

  • 需求源：Phase1-神经期/需求设计文档.md（统一入口 + 鉴权 + 租户隔离）
  • 代码入口：GatewayApplication、路由与过滤器配置（src/main/resources/application.yml）
  • 关键约定：
  • 路由 /api/session/** /api/sense/** /api/nlp/** /api/body/** → lb://<service>
  • 业务服务不得信任请求参数里的租户 ID，一律由网关注入 X-Tenant-Id
  • 开发令牌端点 loopback-only，默认关闭，需 DEV_TOKEN_ENDPOINT_ENABLED=true
  • 测试：网关过滤链 2 项（gateway-service 测试类）
  • 验收标准：跨租户请求被拒；无 token 401；合法 token 透传租户头
  • 开发步骤：①改设计文档 ②改路由/过滤器 ③补过滤链单测（含负向：伪造租户头） ④mvn-dev.sh -pl gateway-service -am test

3.2 会话与 VS1 问答闭环（session-manager，8081）¶

  • 需求源：Phase1-神经期/需求设计文档.md（VS1：session → intent → 本地检索 → 模板回答）
  • 代码入口：SessionController（/api/session/{id}/ask）、OutboundHttp（统一 HTTP/1.1 出站客户端）
  • 关键约定：
  • 出站一律走共享 HTTP/1.1 工厂 + 连接/读超时，不要用 JDK HttpClient 默认的 HTTP/2 （h2c 升级握手会被 uvicorn/h11 拒绝，导致请求体被丢、FastAPI 回 422 → 表面 503，即 D-1 缺陷）
  • 下游不可用时优雅降级：intent → FALLBACK、检索 → 空，并回专用错误码 AGENT_UPSTREAM_UNAVAILABLE
  • 测试：10 项，含 OutboundHttpTest / UpstreamDegradeTest 两个回归守卫
  • 验收标准：POST /api/session/{id}/ask → 200；Redis session:{id}:messages LLEN=2； 停掉 nlp-service 后仍返回 200（FALLBACK）
  • 开发步骤：①改设计 ②实现 + 出站改造 ③补降级回归用例 ④起 Redis/Kafka 实测链路

3.3 感官采集链路（sense-service，8082）¶

  • 需求源：Phase2-感官期/需求设计文档.md（R2-01~R2-10 逐条验收标准与 DoD）
  • 代码入口（按 R 编号）： | 需求 | 入口 | |---|---| | R2-01 渠道抽象 | SenseChannel（Register/Collect/Healthy/Close）+ ChannelRegistry（Spring bean 自动发现） | | R2-02 触觉渠道 | TouchChannel（URL 抓取 + 本地文件 + 纯文本；jsoup 正文提取 + 编码探测） | | R2-03 保留渠道 | VisualChannel / NoseChannel / AudioChannel / TasteChannel —— 诚实上报 available() | | R2-04 归一化 | DataNormalizer（五字段打标：source_channel / tenant_id / timestamp / freshness / confidence） | | R2-05 调度 | R0Scheduler（@Scheduled 规则轮询、每规则独立间隔、日志 + 手动 runNow） | | R2-06 指令处理 | R1DynamicHandler + SenseCommand（指令 → 渠道路由 → 采集 → 响应，单轮渠道上限） | | R2-09 健康与隔离 | ChannelHealthMonitor（探活 + DEGRADED/DOWN 阈值 + 自动隔离 + 恢复跟踪）、resilience4j 指数退避 + DeadLetterStore | | R2-10 暂存 | StagingStore（MinIO/本地双后端、入库前质检闸门、批量回滚） | | R-C02 控制台 | SenseAdminController：/channels、/channels/{type}、/channels-health、/stats、/batches、/batches/{id}/rollback、/rules、/deadletters |
  • 关键约定：渠道能力不可用时必须诚实上报（available=false / DEGRADED），绝不伪造结果
  • 测试：53 项（全项目第二多，含 common/GlobalExceptionHandlerTest 5 项路由层错误语义回归）
  • 验收标准：R2-01~R2-10 逐条对照 DoD；健康监控能在渠道挂掉后隔离并进入死信
  • 开发步骤：①先补需求设计文档的 R 条目与 DoD ②实现渠道/组件并注册 bean ③补单测 ④mvn-dev.sh -pl sense-service -am test ⑤补 docs/demo/Phase2-DEMO.md 的演示步骤

3.4 意图识别（nlp-service，8000）¶

  • 需求源：Phase2-感官期/需求设计文档.md（R2-07 规则引擎、R2-08 L0 + 级联）
  • 代码入口：app/intent/rules.py（关键词/正则/场景规则，覆盖 12 场景，要求 ≥10）、 app/intent/l0_model.py（轻量 L0 分类器）、app/intent/cascade.py（规则优先 → L0 兜底）、app/intent/corpus.py（留出集）
  • 验收标准（已实测）：留出集准确率 90.0%（要求 ≥85%）；P99 0.052 ms（要求 <50 ms）
  • 测试：tests/test_intent.py 15 项
  • 开发步骤：①新场景先加进 rules.py 的场景表并同步 corpus.py 留出集 ②跑 test_intent.py 看准确率是否守住 ③改语料后必须重跑准确率，别只跑通不测指标

3.5 OCR（nlp-service / app/ocr.py）¶

3.5b 嵌入 / 重排 / 分块（nlp-service）—— Phase 3 已交付¶

  • 需求源：Phase3-躯体期/需求设计文档.md（R3-02 分块、R3-03 嵌入、R3-06 重排）
  • 代码入口：app/embedding.py（POST /api/nlp/embed + /embed/health）、 app/reranker.py（POST /api/nlp/rerank + /rerank/health）、app/chunking.py（POST /api/nlp/chunk）
  • 关键约定：
  • 诚实降级：引擎链逐个探测（BGE-M3 → 确定性 hash n-gram 768 维），上报 backend 与 degraded；不可用时不伪造结果
  • 分块与 Java 同算法：改 chunking.py 必须同步 services/java/body-service/.../chunk/ChunkProcessor.java，否则跨语言校验失效
  • 错误出口统一信封（2026-09-18 对齐）：app/main.py 的三个 @app.exception_handler 把 HTTP 层异常、请求体校验失败、兜底异常分别映射为 {code,message,details}； 422 一律归并为 400，使状态码语义与 Java/BFF 一致（路径不存在才 404、方法不支持才 405）
  • 测试：tests/test_embedding.py 13 项 · tests/test_rerank.py 8 项 · tests/test_chunking.py 12 项 · tests/test_http_errors.py 10 项（HTTP 层错误语义，2026-09-18 新增，此前该层零覆盖）
  • 开发步骤：①改模块 ②pytest -q ③若动分块规则，两语言都要改并各自跑测试

3.5c Function Calling 适配（nlp-service / app/tools/）—— Phase 5 已交付¶

  • 需求源：Phase5-四肢期/需求设计文档.md（R5-06）
  • 代码入口：app/tools/function_calling.py —— 把 tool-executor 的工具 schema 转成 LLM 可用的 function-calling 描述（名称 / 参数 schema / 描述），供大脑层决策链在需要时发起工具调用
  • 关键约定：
  • schema 单一真相：以 contracts/tool-schema-baseline.json 与 tool-executor 的 ToolBootstrap 为准， Python 侧只做格式转换，不另立工具清单
  • 不臆造工具：转换失败的条目跳过并留痕，不静默补默认值
  • 测试：tests/test_function_calling.py
  • 开发步骤：①新增内置工具时先改 Java ToolBootstrap + 契约基线 ②同步 Python 转换 ③pytest -q

3.6 躯体服务（body-service，8083）—— Phase 3 已交付¶

  • 需求源：AGENT_CONTEXT/Phase3-躯体期/（R3-01~R3-09 + 终端线 R-C03）
  • 代码入口：
  • 入库链路：IngestService → DocumentParser（格式解析：md/text/html 归一化，PDF/DOCX 显式拒绝）→ ChunkProcessor（分块）→ EmbeddingClient（HTTP → nlp-service）→ QdrantClient（向量）+ PgMetadataStore（元数据）
  • 检索链路：RetrievalService（HotCacheStore 缓存优先 → Qdrant 召回 → RerankClient 重排）
  • 生成链路：RagPipeline（回答 + 可回溯引用）
  • 存储门面：StorageFacade + TierRouter（分层阈值可配）· 装配：BodyStorageConfig
  • 对外：KnowledgeController —— POST /api/body/knowledge（单篇）、POST /api/body/knowledge/batch（批量，单篇失败不影响其余）、GET /api/body/knowledge（列表）、DELETE /api/body/knowledge/{docId}、POST /api/body/retrieve、POST /api/body/retrieve/plan（IN-05 预留）、POST /api/body/rag/answer（注意不是 /api/body/rag，后者无映射会 404）、GET /api/body/knowledge/stats、GET /api/body/knowledge/reconcile（三层对账）、GET /api/body/health
  • 事件闭环：SenseCollectedConsumer 订阅 lifeform.sense.collected
  • 错误出口：common/GlobalExceptionHandler（业务 + 路由层 404/405/415 分流，见 07-运行时配置与横切约定.md §5.1）
  • 关键约定：
  • 分块算法跨语言一致：Java ChunkProcessor 与 Python app/chunking.py 必须同规则（标题/段落边界、800/50、标题入块），否则跨语言校验失去意义
  • Qdrant point id 必须是整数或 UUID：本实现用 UUID.nameUUIDFromBytes(docId#index)（name-based UUID）保证重入库幂等；改这段务必同步 QdrantClientTest
  • 诚实降级：嵌入/重排引擎缺失时走确定性后端并上报 backend/degraded，不伪造
  • 不产脏知识：不支持的格式（PDF/DOCX）显式报错，绝不按纯文本静默分块
  • 启动需显式端口：本机环境变量会污染 server.port → --server.port=8083；PG 凭据须与 docker-compose.yml 一致（agent/agent123）
  • 测试：10 个测试类 60 项（格式解析 / 分块 / 分层 / 缓存 / 内存元数据 / 存储门面对账 / 入库 / 检索 / Qdrant id / 路由层错误语义）
  • 验收标准：见 docs/demo/Phase3-DEMO.md 与《Phase3-测试验收报告》；端到端 35 项、P99 < 500ms、缓存命中 ≥ 30%、租户隔离
  • 开发步骤：①改代码 ②mvn -pl body-service -am test ③起中间件做端到端（.workbuddy/tmp/phase3-e2e.py）④更新 docs/java-services/06-body-service.md 与阶段文档

  • 错误出口：common/GlobalExceptionHandler + common/ErrorCode（与 contracts/work-platform-bff-openapi.yaml 工具域错误码同源）
  • 关键约定：

  • 沙箱诚实降级：Docker 后端不可用才回落受限进程，并在 /api/tool/sandbox 上报 backend/degraded，不谎报隔离
  • 写路径鉴权：POST /api/tool/execute 会真实执行工具，经 BFF 时与 start/stop 同级校验（来源白名单 + X-WP-Control-Token）
  • 启动需显式端口：--server.port=8084（同 body-service，避免环境变量污染）
  • 测试：10 个测试类（注册/版本/影响面、守卫闸门、执行与超时、沙箱后端选择与降级、审计与指标、控制层错误语义）
  • 验收标准：见 docs/demo/Phase5-DEMO.md 与《Phase5-测试验收报告》；注册表可查、执行可审计、沙箱状态可观测、影响面可回放
  • 开发步骤：①改代码 ②mvn -pl tool-executor -am test ③python scripts/contract-check.py --work-platform ④更新 docs/java-services/09-tool-executor.md 与阶段文档

3.8 Ops BFF 与观测区（services/node/wp-bff，8090）¶

  • 需求源：WP-工作平台 + 「观测区」需求（中间件监控 / 链路追踪）+ 躯体视图（/knowledge）
  • 代码入口：server.js（createServer(options)，spawn/probe/fetch 可注入以便测试）、test/server.test.js
  • 端点清单：GET /healthz · GET /overview · GET /middleware · POST /middleware/:key/start|stop · GET /tracing · GET /knowledge · POST /knowledge/search · GET /tools / /tools/registry / /tools/audit / /tools/audit/stats / /tools/metrics / /tools/sandbox · POST /tools/execute · GET /models · POST /models · POST /models/reload · PATCH /models/{id} · DELETE /models/{id} · POST /models/{id}/test（均登记进 IMPLEMENTED_ENDPOINTS）
  • 关键约定：
  • 控制端点（start/stop）必须同时过来源检查（WP_BFF_ALLOWED_ORIGINS）与 控制令牌（X-WP-Control-Token，timingSafeEqual 比较）；缺失/错误 → 401，外来来源 → 403， 两种情况都写审计日志 REJECT_AUTH
  • 令牌来源：WP_BFF_CONTROL_TOKEN，否则启动时随机生成写入 logs/wp-bff-control-token（0600）并打印一次； 没有免鉴权回退模式
  • CORS：不要回 Access-Control-Allow-Origin: *，只对白名单来源回显并始终带 Vary: Origin
  • 命令形状固定 + 8 键白名单；未登记的 key → 403
  • Vite 代理在服务端读令牌文件再注入请求头 → 令牌不进浏览器包；且不重写 Origin（保持 CSRF 检查有效）
  • 鉴权按方法判定，不按路径：只读（GET，以及只读语义的 POST /knowledge/search）免控制令牌，但需透传 X-Tenant-Id（租户隔离）；写路径 POST /knowledge（以及 Phase 5 的 POST /tools/execute）会真实改动知识库 / 真正执行工具，必须与 /middleware/{key}/start|stop 同级校验（来源白名单 + X-WP-Control-Token）。开发环境由 Vite 代理对 /api/wp/* 统一注入令牌，前端无需处理——但直连 8090 会被 401/403 拒绝**，这是有意的（曾因沿用只读豁免短暂出现无鉴权写入后门，已修复）
  • 错误语义与全平台一致（2026-09-18 对齐）：错误体统一为 {code,message,details}； 路由层分流 —— 路径不存在 → 404 AGENT_NOT_FOUND，路径存在但方法不支持 → 405 AGENT_METHOD_NOT_ALLOWED + Allow 头。 该分流由 ROUTE_GUARD 实现，由 IMPLEMENTED_ENDPOINTS 派生（不另立第三份端点真相）， 因此新增端点只需登记一处。完整异常语义见 docs/异常流程归纳.md §2.2
  • 固定段必须排在参数路由之前（/tools/{name} 与 /models/{model_id} 同一类陷阱）： POST /models/reload 会被 /models/{model_id} 吃掉 → 保留段清单由 MODEL_RESERVED_SEGMENTS 从 IMPLEMENTED_ENDPOINTS 派生，不手工维护第二份
  • 4xx 响应体必须原样透出：模型写路径用 httpRequestJsonDetailed() 而非普通 httpRequestJson()， 好让上游的 409 AGENT_CONFLICT 完整到达前端（"哪个字段冲突"不能被吞成通用 500）
  • 测试：node --test test/server.test.js 100 项（鉴权、CSRF、白名单、命令形状、幂等、CORS、链路回落、采样元数据、躯体读端点与降级、知识写路径鉴权反向用例、404/405 错误语义与 ROUTE_GUARD 同源性、Phase 5 工具域读端点与执行代理、子请求失败原因分类 timeout / unreachable / endpoint_missing / http_error / bad_json、WB-10 模型域读写（401/403 反向用例、409 透传、503、保留段、405、OVERVIEW_GAPS 不失真））

    ⚠️ 必须传文件路径（node --test test/server.test.js）。传目录 node --test test/ 会 MODULE_NOT_FOUND。

  • 开发步骤：①改契约（x-wp-status）②改 server.js ③补回归用例 ④node --test ⑤实测 curl 一次真实端点

3.12 跨服务超时预算（contracts/timeout-budget.yaml + scripts/timeout-budget-check.py）¶

  • 为什么单独成节：超时错配不触发任何功能断言 —— 单测全绿、契约 0 FAIL， 只在两个预算的差值里静默降级（把「慢」叙述成「不可用」）。2026-09-19 因此连踩两次， 故把它变成机器门禁，而不是靠人记得住。
  • 权威登记表：contracts/timeout-budget.yaml —— 每条跨服务边一行记录 上游预算与下游最坏耗时两个数字（加上耗时依据、代码锚点、状态）。 当前 19 条边：ok=16 · gap=3 · fail=0（gap 为已登记未修的倒挂，门禁列出但不判失败）。
  • 不变量：上游预算 ≥ 下游最坏耗时 × 1.5。豁免的两类边需显式 exempt_headroom: true （docker 启停 watchdog / TCP 健康探针 —— 它们的超时是预期结果而非失败）。
  • 三层门禁（scripts/timeout-budget-check.py）：
层 内容 防的是
① 语义 上游 ≥ 下游最坏 × 1.5 预算倒挂
② 锚点 按登记表正则从真实代码提实值比对 「表里写 A、代码是 B」
③ 魔法数字 扫调用点禁止就地写数字 ②的盲区（锚点只看常量定义）
  • wp-bff 调用纪律：新增跨服务调用必须用命名档位 （READ / RETRIEVE / GENERATE / WRITE / EXECUTE / SANDBOX_PROBE / MIDDLEWARE_*）， 不得就地写 timeoutMs: 30000。生成型链路（会触发 LLM）必须显式声明 GENERATE 档； 读型端点必须保持短预算 —— 一刀切拉长会让真实故障等 45s 才暴露降级。两条都有 wp-bff 用例守着。
  • 开发步骤：①改代码 ②cd services/node/wp-bff && node --test ③改登记表 ④python scripts/timeout-budget-check.py ⑤改任一侧后必须同步另一侧，否则门禁红
  • 反向验证（改门禁时必做）：门禁绿不等于门禁有效 —— 把档位改成不足值应 FAIL、把调用点换回字面值应报 MAGIC。 实测记录见 docs/优化日志/2026-09-19-跨服务超时预算登记表与门禁落地.md §6.2

3.13 文档一致性（scripts/doc-consistency-check.py）¶

  • 为什么单独成节：本仓的文档坑反复以同一形状出现 —— 约束写在文档里、但没人守。 2026-09-19 实测：给 docs/异常流程归纳.md 追加异常条目时取了已在用的 D-17~D-21， 文档照常渲染、门禁全绿，撞号静默存在，直到人工 grep | uniq -d 才发现。
  • 三类检查：
检查 防的是什么
① 异常编号唯一 D-xx 撞号（该文件 §3 的 D 组）
② 章节号唯一 ### 3.3 出现两次（插入新章节后忘记顺延）
③ md↔html 孪生同步 改了 .md 忘了重生 .html，页面停在旧口径
  • 编号约定（写在该文件 §3 开头）：D-xx 按新增时间递增，与章节顺序不同步； 唯一硬约束是全局唯一。新增条目前先 grep -o '^| D-[0-9]*' docs/异常流程归纳.md | sort | uniq -d 确认无撞号。
  • 本门禁只查「编号撞号」与「孪生过期」，不查内容准确性 —— 用例数 / 行数 / 端点计数仍须拿实测输出对。
  • 用法：python scripts/doc-consistency-check.py；CI 里 html 未落盘时加 --no-twin。
  • 开发步骤：①改 md ②重生孪生（md2html-report.py <file>）③跑本门禁
  • 反向验证（改门禁时必做）：植入撞号应 FAIL、植入重复章节号应 FAIL、只改 md 不重生 html 应报孪生过期。
