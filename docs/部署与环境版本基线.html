6. 标准部署流程¶

# 1. 环境检查
pwsh -File scripts/check-toolchain.ps1

# 2. 复制环境变量模板
cp .env.example .env

# 3. 启动基础设施
docker compose up -d

# 4. 验证基础设施
bash scripts/healthcheck.sh

# 5. 启动 Java 服务
cd services/java
mvn -B -ntp test

# 6. 启动 Python 服务
cd services/python/nlp-service
..\venv\Scripts\python.exe -m pytest -q

# 7. 安装并启动工作平台
cd web/work-platform
npm ci
npm run build

生产环境必须使用独立密钥管理系统，不得把 .env、模型 API Key、控制令牌或模型权重提交到 Git。

7. 维护约定¶

  1. 升级 Java、Node、Python、镜像或前端依赖时，先修改清单文件，再修改本文档。
  2. CI 必须执行 check-toolchain 所需的核心组件检查。
  3. 安装指南中的路径以仓库实际结构为准，不复制第二份版本真值。
  4. 外部模型 Key 只允许通过环境变量、CI Secret 或模型配置加密落库注入。

8. 后台服务监控与本地受控启停¶

工作平台新增 后台服务 页面，监控 8 个应用服务：

gateway-service / session-manager / nlp-service / body-service
tool-executor / collab-bus / wp-bff / work-platform

控制面由 wp-bff 提供：

GET  /api/wp/services
POST /api/wp/services/{key}/start
POST /api/wp/services/{key}/stop

安全边界：

  1. 仅允许 APP_SERVICES 白名单中的 key；
  2. 启动命令、参数、工作目录全部由服务端固定，不接受客户端命令；
  3. 写路径仍经过 Origin 白名单 + X-WP-Control-Token；
  4. wp-bff 自身只监控，不允许自停止；
  5. 外部启动的进程无法安全推断 PID，stop 返回 409，不猜测、不误杀；
  6. WP_BFF_APP_CONTROL=false 可关闭控制，只保留监控。
